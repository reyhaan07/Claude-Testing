Part VIIMemory Management

Every process you met in Part II runs in its own address space. Here is how that address space is actually mapped onto physical RAM — the addresses, the page tables, and the hardware that translates one into the other billions of times per second.

Why Memory Management?

Main memory (RAM) is a large array of bytes, each with an address. The CPU fetches instructions and data from it directly. The OS's memory-management job is to (1) give each process the memory it needs, (2) keep processes from reading or writing each other's memory (protection), (3) let more processes run than would fit if each needed all its memory at once, and (4) do all this fast, since every instruction touches memory. The central trick is a level of indirection between the addresses a program uses and the physical locations they end up at.

Logical, Physical, and Virtual Addresses

Logical (virtual) address
The address a program generates and sees — e.g. the value of a pointer. It's relative to the process's own address space, starting conceptually at 0.
Physical address
The real address of a byte in the RAM chips. What the memory hardware actually uses.
Virtual address
Modern synonym for logical address in a system with virtual memory (Part VIII). The full set a process can name is its virtual address space.

The Memory Management Unit (MMU) — hardware in the CPU — translates every logical address to a physical address on the fly, using tables the OS sets up. The program never sees physical addresses; this is what enables both protection and virtual memory.

Address Binding

"Binding" is fixing a program's addresses to real locations. It can happen at three times:

  • Compile time — if you know where the program will load, generate absolute addresses. Rigid (must recompile to move).
  • Load time — the compiler emits relocatable code; addresses are fixed when the program loads.
  • Execution time — binding is deferred until run time and can change as the process moves; this needs hardware (the MMU) and is what modern systems use. It's what makes paging and swapping possible.

Contiguous Allocation

The oldest scheme: give each process a single contiguous block of physical memory.

Fixed (static) partitioning
Divide memory into a fixed number of partitions of preset size. Simple, but a process smaller than its partition wastes the rest (internal fragmentation), and a process larger than any partition can't run.
Variable (dynamic) partitioning
Partitions are created to fit each process exactly. No internal waste, but as processes come and go they leave holes, producing external fragmentation.

Placement strategies for variable partitioning — where to put a new process among the holes:

  • First fit — first hole big enough. Fast.
  • Best fit — smallest hole that fits. Minimizes leftover, but leaves many tiny unusable holes.
  • Worst fit — largest hole. Leaves big usable leftovers (usually performs poorly in practice).

Compaction shuffles processes together to merge scattered holes into one big free block. It works only with execution-time binding (addresses can change), and it's expensive (lots of copying). The real cure for external fragmentation is paging, which drops the "contiguous" requirement entirely.

⚠Common Mistake
Swapping the two fragmentations. Mnemonic: Internal = wasted space inside a block you were given. External = usable space exiled into scattered holes external to any allocation. Paging eliminates external fragmentation but introduces a little internal fragmentation (the last partial page).

Paging

The big idea. Stop requiring memory to be contiguous. Chop the process's virtual address space into fixed-size pages and physical memory into equal-size frames (a page and a frame are the same size, typically 4 KB). Any page can go in any free frame; a per-process page table records which frame holds each page. External fragmentation vanishes because any frame fits any page.

▣Key Concept — how an address is split
A logical address is divided into two parts: a page number (high bits) and an offset (low bits) within the page. The page table maps the page number → a frame number; the offset is copied unchanged. With page size 2k, the low k bits are the offset.
physical address = frame_number × page_size + offset

Worked example. Page size = 4 KB = 212 bytes (so offset = 12 bits). Consider logical address 8196:

  • page number = 8196 ÷ 4096 = 2;   offset = 8196 mod 4096 = 4.
  • Suppose the page table says page 2 → frame 8.
  • physical address = 8 × 4096 + 4 = 32772.
⚠Common Mistake
Thinking paging needs no translation cost. Naive paging doubles memory latency: one access to read the page table (in RAM) plus one to reach the actual data. That's exactly the problem the TLB solves.

The TLB (Translation Lookaside Buffer)

What & why. Since the page table lives in RAM, every memory reference would need an extra RAM access just to translate — halving performance. The TLB is a small, very fast associative cache inside the MMU that remembers the most recent page→frame translations.

  • TLB hit — translation found in the TLB; frame number returned in ~1 cycle. Fast path.
  • TLB miss — not cached; the MMU walks the page table in RAM (slow), then loads the result into the TLB for next time.
Effective Access Time = Phit(TLB + mem) + Pmiss(TLB + 2×mem)

Numerical: TLB access 10 ns, memory access 100 ns, hit ratio 90%. EAT = 0.9×(10+100) + 0.1×(10+200) = 99 + 21 = 120 ns — versus 200 ns with no TLB. Real TLB hit rates exceed 99%, thanks to locality (Part VIII).

▣Key Concept
The TLB is why paging is practical. It exploits locality of reference: programs keep touching the same few pages, so a tiny cache of recent translations catches almost every access. On a context switch the TLB may be flushed (translations belong to the old process's page table) — one of the hidden costs of switching processes.

Multi-Level and Inverted Page Tables

The problem: a single flat page table for a 32-bit address space with 4 KB pages needs 220 ≈ 1 million entries per process — megabytes of table, mostly unused. Two solutions:

Multi-level (hierarchical) page tables
Page the page table itself. An outer table points to inner tables, which point to frames. Unused regions simply have no inner table, saving space. x86-64 uses four levels. Cost: a TLB miss now walks several levels (more memory accesses) — mitigated by the TLB.
Inverted page table
One table for the whole system, with one entry per physical frame (not per virtual page). Saves enormous space, but looking up "which frame holds page p of process X" requires searching — so it's paired with a hash table.

Segmentation

What. Instead of fixed-size pages, divide a program by its logical parts — segments like code, data, stack, heap — each a variable-length unit meaningful to the programmer. A logical address is <segment number, offset>; a segment table stores each segment's base and limit. This matches how programmers think and eases protection/sharing per segment (e.g. code read-only, shared between processes).

Downside: variable-size segments bring back external fragmentation (like variable partitioning). Pure segmentation is largely historical; modern systems use paging, sometimes segmentation with paging (segments divided into pages) to get both worlds.
