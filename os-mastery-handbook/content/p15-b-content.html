Part XVAdvanced Operating Systems

Everything so far runs one OS on one machine. This part scales that up and locks it down: how one machine runs many operating systems, how thousands of containers share one kernel safely, and the kernel mechanisms — modern scheduling, NUMA, ASLR, the page cache — behind today's servers.

Virtualization and Hypervisors

What. Virtualization runs a whole "virtual machine" (VM) — a complete guest OS with its own virtual CPU, memory, and devices — as software on a host. A hypervisor (Virtual Machine Monitor) is the layer that creates and manages VMs, giving each the illusion of owning the hardware while multiplexing the real hardware among them. It's the OS's "resource manager" and "extended machine" ideas (Part I) applied to entire operating systems.

Type 1 (bare-metal)
Runs directly on the hardware; guests sit on top. Fast, used in data centers. Examples: VMware ESXi, Xen, Microsoft Hyper-V, KVM (turns Linux itself into a Type-1-like hypervisor).
Type 2 (hosted)
Runs as an application on a normal host OS. Convenient for desktops. Examples: VirtualBox, VMware Workstation.

Hardware assists (Intel VT-x, AMD-V) let guest kernels run privileged instructions safely by trapping into the hypervisor — the same dual-mode idea from Part I, extended with an extra privilege level for the hypervisor beneath the guest kernel.

Containers: Namespaces and cgroups

The key difference from VMs. A VM virtualizes hardware and runs a full guest kernel. A container virtualizes the operating system: containers share the host's single kernel but each gets an isolated view of the system. Containers are therefore far lighter (no guest OS to boot, megabytes not gigabytes, start in milliseconds) — at the cost of weaker isolation (a shared kernel is a shared attack surface).

Containers are built from two Linux kernel features:

Namespaces — isolation ("what a process can see")
Give a process group its own private view of a system resource. There are namespaces for PIDs (a container sees its own process 1), the mount table (its own filesystem view), the network (its own interfaces/ports), users, hostname (UTS), and IPC. Two containers can each have a "PID 1" because they're in different PID namespaces.
Control groups (cgroups) — limits ("what a process can use")
Meter and cap a process group's CPU, memory, and I/O. A cgroup can say "this container gets at most 2 cores and 512 MB." This is the resource-manager role of the OS (Part I) exposed as a policy knob.
▣Key Concept — Docker from an OS perspective
A Docker container is not a lightweight VM. It's an ordinary Linux process (or group of them) running on the host kernel, wrapped in namespaces (so it sees only its own PIDs, filesystem, network) and cgroups (so its CPU/memory are capped), using a union filesystem (layered images) for its root filesystem. Nothing is emulated — it's your kernel's isolation features, packaged. That's why containers start instantly and run at native speed.

Kernel Modules

A loadable kernel module is a piece of kernel code (often a device driver) that can be added to or removed from a running kernel without rebooting or recompiling. This is what makes Linux a modular monolithic kernel (Part I): the core is monolithic, but drivers and features plug in on demand.

Managing kernel modules$ lsmod                    # list currently loaded modules
$ sudo modprobe e1000e     # load a network driver (+ dependencies)
$ sudo rmmod e1000e        # unload it
$ modinfo e1000e           # info about a module

System Initialization

After the kernel boots (Part I), it starts exactly one user process: PID 1, the init system. On modern Linux this is systemd. PID 1 is the ancestor of every other process; it launches system services (daemons), mounts filesystems, brings up networking, and adopts orphans (Part II). systemd organizes services as units with dependencies and starts independent ones in parallel for fast boot.

Interacting with the init system$ systemctl status sshd    # is the SSH daemon running?
$ systemctl start/stop/restart nginx
$ systemctl enable nginx    # start automatically at boot
$ journalctl -u nginx       # view that service's logs

Modern Scheduling and NUMA

CFS. Linux's long-time default scheduler was the Completely Fair Scheduler. Instead of fixed time slices, CFS tracks each task's virtual runtime (vruntime) — roughly, how much CPU it has consumed, weighted by nice value — and always runs the task with the smallest vruntime, using a red-black tree to pick it in O(log n). The effect: every task gets a fair share of the CPU over time, approximating "infinitely fine" time-slicing. (Newer kernels use EEVDF, a refinement of the same fairness goal.)

NUMA. On multi-socket servers, memory is Non-Uniform Memory Access: each CPU has "local" RAM it reaches quickly and "remote" RAM (attached to another CPU) it reaches more slowly. A NUMA-aware OS tries to run a thread on the CPU near the memory it uses, and to allocate a process's memory on its local node — because a remote memory access can be several times slower. It's the memory hierarchy (Part VII) extended across CPU sockets.

Kernel Memory Features: Page Cache, ASLR, mmap I/O, COW

Page cache
The kernel caches file contents in otherwise-free RAM (Part VIII). A re-read of a file is served from memory, not disk — the buff/cache you saw in free (Part XIV). Writes are buffered and flushed later. This one feature is why a warm system feels so much faster than a cold one.
Memory-mapped I/O
Via mmap (Part VIII), a file or device is mapped into a process's address space so accessing it is just memory access — avoiding read/write syscalls and extra copies. It's how program executables and shared libraries are loaded (demand-paged directly from disk).
Copy-on-Write
Recap from Part VIII: fork() and shared libraries share physical pages read-only and duplicate only on write — the trick that makes process creation and library sharing cheap.
ASLR
Address Space Layout Randomization: the kernel randomizes where a process's stack, heap, libraries, and (with PIE) code are placed in its virtual address space on each run. Because attackers exploiting a buffer overflow need to know target addresses, randomizing them makes many exploits unreliable. A cheap, powerful security-through-uncertainty layer built on virtual memory.
⚑Interview Tip
"How does a container differ from a VM?" One sentence: a VM virtualizes hardware and runs its own guest kernel via a hypervisor; a container shares the host kernel and is isolated by namespaces (visibility) and cgroups (resource limits). Then the trade-off: VMs give stronger isolation and can run different OSes; containers are lighter and faster but share one kernel. That crisp distinction is asked constantly in cloud/DevOps interviews.

Kernel/User-Space Communication

How does user code exchange information with the kernel, beyond ordinary system calls? A quick map:

  • System calls — the primary, synchronous request path (Part I).
  • /proc and /sys — read/write kernel and device state as files (Part XIV).
  • ioctl — device-specific control operations on a file descriptor.
  • mmap — share a memory region between kernel and user space (zero-copy).
  • Signals — kernel → process asynchronous notifications (Part XI).
  • Netlink sockets — a socket-based channel for configuration/events (used for networking config).
