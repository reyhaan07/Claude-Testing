Part VProcess Synchronization

In Part III you saw counter++ lose updates when two threads race. Here you learn to stop that — precisely, correctly, and without creating new problems like deadlock. These primitives are the vocabulary of every concurrent program you will ever write.

The Critical-Section Problem

Recall the race: shared data touched by concurrent threads, at least one writing, with a non-atomic operation in the middle. The region of code that touches the shared data is the critical section. The goal is to allow only one thread inside it at a time — mutual exclusion — without breaking two other guarantees.

▣Key Concept — the three requirements of a correct solution
1. Mutual Exclusion. At most one thread executes in the critical section at a time.
2. Progress. If no thread is in the critical section and some want in, the choice of who enters cannot be postponed indefinitely — a thread not interested must not block others.
3. Bounded Waiting. There is a limit on how many times other threads enter before a waiting thread gets its turn — no starvation.

Every lock, semaphore, and monitor exists to satisfy these three at once. A "solution" that provides mutual exclusion but allows starvation (violates bounded waiting) is wrong.

Atomic Operations

What & why. An atomic operation executes as a single, indivisible step — it cannot be interrupted halfway, so no other thread can see a partial result. Atomicity is the bedrock: if counter++ were atomic, there would be no race. Since it isn't, the hardware provides atomic primitives that locks are built from:

  • Test-and-Set — atomically read a flag and set it to 1, returning the old value.
  • Compare-and-Swap (CAS) — atomically: "if memory == expected, set it to new; return success." The workhorse of modern lock-free programming.
  • Fetch-and-Add — atomically add to a memory location and return the old value.
A spinlock built from atomic test-and-set (concept)int lock = 0;                       // 0 = free, 1 = held

void acquire() {
    while (test_and_set(&lock) == 1)  // atomically: old=lock; lock=1; return old
        ;                             // spin: keep trying until we saw 0
}
void release() { lock = 0; }         // hand it back

Locks and Mutexes

A mutex (MUTual EXclusion lock) is the simplest synchronization object: it is either locked or unlocked, and it has an owner. A thread lock()s it before the critical section and unlock()s it after. Only the thread that locked it may unlock it. If another thread tries to lock a held mutex, it blocks (sleeps) until the owner releases.

Fixing the Part III race with a pthread mutex#include <pthread.h>

long counter = 0;
pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;

void *worker(void *arg) {
    for (int i = 0; i < 1000000; i++) {
        pthread_mutex_lock(&m);       // ENTRY: only one thread past here
        counter++;                    // CRITICAL SECTION (now safe)
        pthread_mutex_unlock(&m);     // EXIT: let the next thread in
    }
    return NULL;
}
// Now the final counter is EXACTLY N * 1000000, every single run.
⚠Common Mistake
Locking too much or too little. Lock too little (leave a shared write unprotected) and the race persists. Lock too much (hold the mutex across slow I/O) and you serialize everything, killing concurrency. Hold locks for the shortest correct span — protect the shared data, nothing more.

Spinlocks: Busy Waiting vs Blocking

When a lock is held, a waiting thread can do one of two things:

Busy waiting (spinlock)
Loop, repeatedly checking the lock ("spinning"), burning CPU while it waits. No context switch, so it's fast if the wait is very short.
Blocking (mutex)
Give up the CPU and sleep; the OS wakes the thread when the lock frees. Wastes no CPU, but pays two context switches (sleep + wake).

⚑Interview Tip
"Spinlock vs mutex?" A spinlock busy-waits; a mutex sleeps. Spinlocks win only when the critical section is shorter than the cost of two context switches and you have multiple cores (so the holder can run on another core while you spin). On a single core, spinning is pointless — the thread holding the lock can't make progress while you monopolize the CPU spinning. Real kernels use hybrid "adaptive" locks that spin briefly, then sleep.

Semaphores

What is it? A semaphore is an integer counter with two atomic operations, invented by Dijkstra. wait() (also P, or down) decrements it, blocking if it would go negative; signal() (also V, or up) increments it, waking a waiter. The counter tracks "how many units of a resource are available."

Semaphore semantics (atomic)wait(S):   // P — acquire
    while (S <= 0) ;   // block until a unit is available
    S = S - 1;

signal(S): // V — release
    S = S + 1;         // wake a blocked waiter if any
Binary semaphore
Counter is only 0 or 1. Acts like a lock (mutual exclusion). But unlike a mutex, it has no owner — any thread may signal it.
Counting semaphore
Counter ranges over 0..N, representing N identical resource units (e.g. "5 database connections available"). Threads wait() to take one, signal() to return one.
▣Key Concept — two distinct uses of semaphores
(1) Mutual exclusion: a binary semaphore initialized to 1 guards a critical section. (2) Signaling / ordering: a semaphore initialized to 0 makes one thread wait for another to reach a point (thread A does signal, thread B's wait unblocks). This second use — enforcing an order between threads — is something a plain mutex cannot do, and it's the key to producer–consumer.

▣Key Concept — Mutex vs Semaphore in one line
A mutex is a locking mechanism (ownership; used for mutual exclusion). A semaphore is a signaling mechanism (a counter; used to coordinate/count). Every mutex can be built from a binary semaphore, but a mutex adds ownership. Use a mutex to protect data; use a semaphore to count resources or to make one thread wait for an event in another.
⚠Common Mistake
"A binary semaphore is just a mutex." Not quite — the difference is ownership. A mutex can only be unlocked by the thread that locked it; a binary semaphore can be signaled by any thread. That makes the semaphore usable for signaling between threads, but also makes it easier to misuse (e.g. accidentally signal twice). This exact distinction is a favorite trap question.

Monitors and Condition Variables

Semaphores are powerful but error-prone: forget a signal, or order two waits wrongly, and you deadlock — with no compiler help. A monitor is a higher-level construct that bundles shared data and the operations on it, guaranteeing that only one thread is active inside the monitor at a time (automatic mutual exclusion). Languages provide them directly: Java's synchronized, C#'s lock.

Inside a monitor, condition variables let a thread wait for a condition without busy-waiting:

  • wait(cv) — atomically release the monitor lock and sleep until signaled.
  • signal(cv) — wake one thread waiting on cv.
  • broadcast(cv) — wake all of them.
⚠Common Mistake
Checking a condition with if instead of while before wait(). After waking, a thread must recheck the condition in a loop, because (a) another thread may have changed it first (spurious/ stolen wakeups). Always: while (!ready) cond_wait(&cv,&m);

Classic Problem 1 — Producer–Consumer (Bounded Buffer)

Problem. A producer thread creates items and puts them in a fixed-size buffer; a consumer takes them out. Why it's hard: the producer must wait if the buffer is full; the consumer must wait if it's empty; and both mutate the buffer, so access must be mutually exclusive.

Naive (broken) approach: a single mutex around the buffer. It prevents corruption but doesn't handle full/empty — the producer would spin-fail on a full buffer, wasting CPU, and there's no clean way to wait for space. Correct approach: two counting semaphores to track space and items, plus a mutex for exclusion.

Producer–Consumer with semaphores (the canonical solution)sem_t empty;   // counts free slots; init to N (buffer size)
sem_t full;    // counts filled slots; init to 0
pthread_mutex_t mutex;  // protects the buffer; init unlocked

void producer() {
    while (1) {
        item = produce_item();
        sem_wait(&empty);          // wait for a free slot  (blocks if full)
        pthread_mutex_lock(&mutex);
        buffer_put(item);          // CRITICAL SECTION
        pthread_mutex_unlock(&mutex);
        sem_post(&full);           // announce one more item
    }
}
void consumer() {
    while (1) {
        sem_wait(&full);           // wait for an item  (blocks if empty)
        pthread_mutex_lock(&mutex);
        item = buffer_get();       // CRITICAL SECTION
        pthread_mutex_unlock(&mutex);
        sem_post(&empty);          // announce one more free slot
        consume_item(item);
    }
}
⚠Common Mistake — deadly ordering bug
Never lock the mutex before the semaphore wait. If the producer does lock(mutex) then wait(empty) on a full buffer, it sleeps holding the mutex; the consumer can never lock the mutex to remove an item → deadlock. Order is always: wait(counting semaphore) first, then lock(mutex).

Classic Problem 2 — Readers–Writers

Problem. A shared resource (e.g. a database) may be read by many threads simultaneously (reads don't conflict), but a writer needs exclusive access (writes conflict with everything). Maximize concurrency: allow concurrent readers, but a writer must be alone.

Correct approach (reader-preference): a mutex for the resource, a counter of active readers, and a mutex protecting that counter. The first reader in "locks out" writers; the last reader out releases them.

Readers–Writers (reader preference)int readers = 0;
pthread_mutex_t rc;          // protects the readers counter
sem_t rw;                    // exclusive access to the resource; init 1

void reader() {
    pthread_mutex_lock(&rc);
    if (++readers == 1) sem_wait(&rw); // FIRST reader blocks writers
    pthread_mutex_unlock(&rc);

    read_resource();                     // many readers here at once

    pthread_mutex_lock(&rc);
    if (--readers == 0) sem_post(&rw); // LAST reader frees writers
    pthread_mutex_unlock(&rc);
}
void writer() {
    sem_wait(&rw);            // exclusive: wait for zero readers AND no writer
    write_resource();
    sem_post(&rw);
}

Trade-off / common mistake: this reader-preference version can starve writers — a steady stream of readers never lets readers hit 0. Production solutions use writer-preference or a fair queue to guarantee bounded waiting for writers.

Classic Problem 3 — Dining Philosophers

Problem. Five philosophers sit around a table; one fork between each pair (five forks). To eat, a philosopher needs both adjacent forks. This models processes competing for multiple shared resources — and it's the canonical way to produce (and study) deadlock.

Naive (deadlocking) approach: everyone picks up their left fork, then their right. If all five grab their left fork simultaneously, each holds one and waits forever for the right — a perfect circular wait (Part VI). Correct approaches that break the circular wait:

  • Resource ordering: number the forks; always pick up the lower-numbered fork first. One philosopher then reaches for forks in the opposite order, breaking the cycle. (Breaks circular wait.)
  • Asymmetry: odd philosophers grab left-then-right, even ones right-then-left.
  • Limit diners: allow at most 4 philosophers to sit at once (a counting semaphore init to 4), guaranteeing at least one can get both forks.
  • Waiter/monitor: a central arbiter grants forks only when both are free (pick up both or neither).
Dining Philosophers — deadlock-free via resource orderingvoid philosopher(int i) {
    int left = i, right = (i + 1) % 5;
    int first = (left < right) ? left : right;   // always lower-numbered fork first
    int second = (left < right) ? right : left;
    while (1) {
        think();
        sem_wait(&fork[first]);      // consistent global order → no cycle → no deadlock
        sem_wait(&fork[second]);
        eat();
        sem_post(&fork[second]);
        sem_post(&fork[first]);
    }
}
⚑Interview Tip
Dining Philosophers is really a deadlock question in disguise. Name the four Coffman conditions (Part VI) and show which your solution breaks: resource ordering and asymmetry break circular wait; "pick up both or neither" breaks hold-and-wait; the ≤4-diners rule ensures at least one philosopher can always proceed. Mentioning the Coffman connection is what earns the senior-level nod.
