Part IIProcesses

Everything a computer does for you happens inside a process. When you open a browser, compile code, or run a server, the OS creates processes, feeds them CPU time, gives each its own protected memory, and cleans up after them. Master the process and half of operating systems falls into place.

Program vs Process

What is it? A program is a passive, static file on disk — a sequence of instructions and data (e.g. /usr/bin/ls). A process is a program in execution: an active entity with its own memory, CPU registers, a program counter, open files, and a unique identity.

Simple intuition. A program is a recipe in a cookbook. A process is you actually cooking it — using a kitchen (memory), your hands (CPU), and a bookmark showing which step you are on (program counter). The same recipe can be cooked by two people at once in two kitchens: one program, two independent processes.

▣Key Concept
Program : Process = Recipe : Cooking. One program can spawn many processes (open your terminal twice — two bash processes from one bash program). A process is a program plus its execution state: memory image, registers, PC, kernel bookkeeping.

The Process Address Space

When the OS launches a process, it gives it a private virtual address space — a fresh, protected view of memory the process believes is entirely its own. That space is organized into segments. Knowing this layout explains stack overflows, malloc, and countless bugs.

Text
The machine code. Read-only (so it can be shared between processes running the same program) and protected from accidental writes.
Data / BSS
Global and static variables. Data holds initialized ones; BSS holds zero-initialized ones (stored compactly as "reserve N zero bytes").
Heap
Dynamically allocated memory (malloc/new). Grows upward as you allocate; managed by the allocator on top of the brk/mmap syscalls.
Stack
Function call frames: local variables, arguments, return addresses. Grows downward; automatically freed as functions return.
⚠Common Mistake
Confusing stack and heap. Locals live on the stack and vanish when the function returns — returning a pointer to a local is a bug. malloc'd memory lives on the heap and survives until you free it — forgetting to free is a memory leak.

The Process Control Block (PCB)

What is it? The Process Control Block is the kernel's data structure that stores everything the OS needs to know about a process. One PCB exists per process; it is the process, as far as the kernel is concerned. (In Linux the PCB is struct task_struct.)

Why do we need it? The CPU can run only one process at a time per core. To pause process A and later resume it exactly where it left off, the OS must save A's complete state somewhere — that somewhere is the PCB.

▣Key Concept
The PCB is the anchor for three big ideas at once: context switching (save/restore its registers & PC), scheduling (its state and priority determine what runs next), and isolation (its memory-management fields point to a private address space). The kernel keeps all PCBs in lists/queues so it can find and manage every process.

Process States and Transitions

A process is not always running — most of the time it is waiting for something (the CPU, or an I/O device). The OS models this with a small set of states. The five-state model is the one to know cold.

New
The process is being created (PCB allocated, memory being set up).
Ready
Loaded and willing to run — just waiting for the CPU. Sits in the ready queue.
Running
Currently executing on a CPU. Only one process per core is here at any instant.
Waiting / Blocked
Cannot proceed until some event happens (disk read completes, a lock is released, input arrives). Not competing for the CPU.
Terminated
Finished executing; the OS is reclaiming its resources.

The key transitions:

  • Ready → Running (dispatch): the scheduler selects the process and gives it the CPU.
  • Running → Ready (preemption): its time slice expired, or a higher-priority process arrived. It is still runnable — just paused.
  • Running → Waiting (block): it requested I/O or a resource that is not ready. It voluntarily gives up the CPU.
  • Waiting → Ready (wakeup): the awaited event happened; it rejoins the ready queue (note: it does not go straight to Running).
  • Running → Terminated: it called exit() or was killed.
⚠Common Mistake
Thinking a process goes Waiting → Running directly when its I/O finishes. It does not — it goes Waiting → Ready, then must be scheduled before it runs. The CPU might be busy with someone else. This distinction matters in scheduling questions.
⚑Interview Tip
Draw the five-state diagram and name every transition and its cause. Then mention that real kernels add states: Linux has TASK_RUNNING (covers ready+running), TASK_INTERRUPTIBLE/UNINTERRUPTIBLE (two flavors of waiting), and TASK_ZOMBIE. Naming real kernel states signals depth.

Process Creation with fork()

What is it? On UNIX/Linux, new processes are born by cloning. The fork() system call creates a near-exact copy of the calling process. The original is the parent; the copy is the child. This builds a process tree rooted at PID 1 (init/systemd).

The famous trick — one call, two returns. fork() is called once but returns twice: once in the parent (returning the child's PID) and once in the child (returning 0). That return value is how each copy knows who it is.

fork() — one call, two processes#include <stdio.h>
#include <unistd.h>
#include <sys/wait.h>

int main(void) {
    pid_t pid = fork();              // clone this process here

    if (pid < 0) {
        perror("fork failed");   // no child was created
    } else if (pid == 0) {
        printf("Child : my PID=%d, parent=%d\n", getpid(), getppid());
    } else {
        printf("Parent: my PID=%d, child=%d\n", getpid(), pid);
        wait(NULL);                 // wait for the child to finish
    }
    return 0;
}

How it works internally. The kernel allocates a new PCB, copies the parent's state (open files, credentials, and a logical copy of its address space), assigns a new PID, and marks the child Ready. Copying all of memory would be wasteful, so modern kernels use copy-on-write (COW): parent and child share the same physical pages, marked read-only; only when one writes does the kernel duplicate that page. This makes fork() cheap. (COW returns in Part VIII.)

⚠Common Mistake
Assuming the parent runs before the child (or vice versa). After fork(), both are Ready and the scheduler decides the order — it is nondeterministic. Never write code that depends on which runs first; use wait() or synchronization if order matters.

Running a New Program with exec()

fork() gives you a copy of the same program. To run a different program, the child calls a member of the exec() family (execl, execvp, execve…). exec() replaces the current process's memory image with a new program — same PID, brand-new text/data/heap/stack. It does not return on success (there is nothing to return to; the old program is gone).

▣Key Concept — the fork/exec pattern
This is how every shell launches every command: fork to create a child, then exec in the child to become the desired program, while the parent waits. Separating "create a process" (fork) from "run a program" (exec) is a deliberate, powerful UNIX design — between the two, the child can redirect I/O, close files, or set up pipes (Part XI).
fork + exec + wait: how a shell runs "ls -l"pid_t pid = fork();
if (pid == 0) {                       // --- child ---
    execlp("ls", "ls", "-l", NULL);   // become 'ls'; never returns if OK
    perror("exec failed");            // only reached on error
    _exit(1);
} else {                              // --- parent (the shell) ---
    int status;
    waitpid(pid, &status, 0);          // block until child finishes
    printf("child exited with %d\n", WEXITSTATUS(status));
}

Termination and wait()

A process ends by calling exit(status) (voluntary) or by receiving a fatal signal like SIGKILL (involuntary). On termination the kernel closes the process's files, frees its memory, and keeps a small exit status around so the parent can learn how the child fared.

The parent collects that status with wait()/waitpid(). This is called reaping. Until the parent reaps it, the dead child lingers as a zombie (next section). wait() also lets a parent synchronize with a child — blocking until it finishes.

Zombies, Orphans, and Daemons

Three special process conditions that interviewers love and beginners confuse. Learn them as a set.

Zombie Process

What: a child that has terminated but whose parent has not yet wait()ed for it. It is dead but still occupies a PCB slot (holding its exit status). Why it exists: so the parent can still read the exit status after the child is gone. Danger: a parent that never reaps its children leaks PCB entries; enough zombies can exhaust the process table. Fix: the parent must wait(), or handle SIGCHLD.

Creating (and observing) a zombiepid_t pid = fork();
if (pid == 0) {
    _exit(0);              // child dies immediately
} else {
    sleep(30);             // parent naps WITHOUT wait() -> child is a zombie
    // run 'ps aux | grep defunct' now: you'll see it as <defunct>
}

Orphan Process

What: a child whose parent terminated first, leaving the child still running. Who adopts it: the kernel reparents orphans to init/systemd (PID 1), which dutifully reaps them when they finish. So orphans are harmless — they always get a responsible foster parent.

Daemon Process

What: a long-running background service with no controlling terminal — web servers, sshd, cron. How it is made: a process forks, the parent exits (so the child becomes an orphan adopted by PID 1), and the child calls setsid() to start a new session, detaching from any terminal. The trailing d in names like sshd, httpd, systemd means "daemon."

⚠Common Mistake
"You kill a zombie with kill -9." You cannot — it is already dead; there is nothing to kill. A zombie disappears when its parent reaps it. If the parent won't, kill the parent; the zombie is then reparented to PID 1, which reaps it instantly.

Context Switching

What is it? A context switch is the act of saving the state of the currently running process and restoring the state of another, so the CPU can switch from running process A to process B. It is the mechanism that makes one CPU appear to run many processes at once.

Simple intuition. A single receptionist (CPU) serving many customers (processes). To switch customers, the receptionist writes down exactly where they left off with customer A (save context), pulls out customer B's file (restore context), and continues. The note-taking itself takes time and serves no customer — that is overhead.

How it works internally. Triggered by a timer interrupt (preemption), a blocking system call, or a higher-priority wakeup, the kernel:

  1. Saves the CPU registers and program counter of A into A's PCB.
  2. Updates A's state (Running → Ready or Waiting) and picks B via the scheduler.
  3. Loads B's registers, PC, and memory context (switches page tables / address space) from B's PCB.
  4. Returns to user mode; B resumes exactly where it last stopped.
⚑Interview Tip
"Why does context switching have overhead?" Two reasons: (1) the direct cost of saving/restoring registers and switching address spaces, and (2) the indirect cost — the new process starts with cold CPU caches and TLB (which may be flushed), so it runs slower until they warm up. This is why excessive switching (e.g. too many threads) hurts performance. Switching between threads of one process is cheaper: same address space, so no page-table switch or full TLB flush.

Scheduling Queues, CPU Bursts, and I/O Bursts

The OS keeps processes organized in queues as they move between states:

  • Job queue — all processes in the system.
  • Ready queue — processes in memory, Ready, waiting for the CPU.
  • Device / wait queues — one per device; processes blocked on that device's I/O.

A process's life alternates between two kinds of activity:

CPU burst
A stretch of computation using the CPU.
I/O burst
A stretch of waiting for input/output (disk, network, user).

This CPU–I/O burst cycle is fundamental to scheduling (Part IV). CPU-bound processes (e.g. video encoding) have long CPU bursts; I/O-bound processes (e.g. a text editor) have short CPU bursts and lots of waiting. Good schedulers favor I/O-bound processes to keep devices busy.

Process Isolation

What & why. Each process gets its own virtual address space, so process A literally cannot see or corrupt process B's memory — a wild pointer in A crashes only A. This isolation is enforced by the hardware MMU (Part VII) under the kernel's control, and it is the reason one misbehaving app doesn't take down your whole machine.

Isolation is a double-edged sword: it keeps processes safe from each other, but it also means they cannot casually share data. To communicate, they need explicit, kernel-mediated mechanisms — which is exactly what inter-process communication provides.

Inter-Process Communication (Overview)

Because processes are isolated, the OS offers controlled channels for them to exchange data. There are two broad families:

  • Shared memory — two processes map the same region of physical memory; fastest, but they must synchronize access themselves.
  • Message passing — processes send/receive discrete messages via the kernel (pipes, message queues, sockets); safer and simpler, but involves copying and system calls.

The full toolkit — pipes, named pipes, message queues, shared memory, signals, sockets, and RPC — with working C examples is Part XI. For now, just hold the idea: isolation is the default; IPC is how you deliberately poke holes in it.
