Part XIInter-Process Communication

A shell command like ps aux | grep ssh quietly relies on IPC: the output of one process becomes the input of another. This part covers every mechanism the OS gives isolated processes to exchange data — from the humble pipe to shared memory — with the trade-offs that decide which to use.

Why IPC? The Two Families

Because each process has a private address space, they cannot simply read each other's variables. IPC provides deliberate, kernel-mediated channels. Every mechanism belongs to one of two families:

Shared memory
Two processes map the same physical memory region into their address spaces; one writes, the other reads — directly. Fastest (no kernel copy after setup), but the processes must synchronize access themselves (Part V) to avoid races.
Message passing
Processes exchange discrete messages through the kernel (send/receive). Simpler and safer (the kernel handles synchronization and delivery), but slower — each message is copied through the kernel.

Pipes and Named Pipes

Pipe. A one-way, in-memory byte stream with two ends: one process writes, another reads. An ordinary (anonymous) pipe is created with pipe() and shared with a child via fork() — which is exactly how the shell wires cmd1 | cmd2. It's a FIFO (first-in-first-out) stream; the kernel buffers it and blocks the writer if it's full or the reader if it's empty.

An anonymous pipe between parent and childint fd[2];                 // fd[0] = read end, fd[1] = write end
pipe(fd);
if (fork() == 0) {        // --- child: reader ---
    close(fd[1]);            // close unused write end
    char buf[64];
    int n = read(fd[0], buf, sizeof buf);
    write(1, buf, n);        // echo to stdout
} else {                  // --- parent: writer ---
    close(fd[0]);            // close unused read end
    write(fd[1], "hello from parent\n", 18);
    close(fd[1]);
}

Named pipe (FIFO). A pipe with a name in the file system (created with mkfifo), so unrelated processes (not just parent/child) can connect to it by opening the path. Otherwise it behaves like an anonymous pipe.

⚠Common Mistake
Leaving both pipe ends open. If the writer never closes its end, the reader's read() never sees end-of-file and can hang forever. Always close() the ends you don't use in each process — the reader gets EOF only when all write ends are closed.

Message Queues

A message queue is a kernel-maintained linked list of discrete messages. Processes send typed/prioritized messages and receive them, and messages persist in the kernel until read (even if the sender exits). Unlike a pipe's raw byte stream, a queue preserves message boundaries and can support priorities. POSIX (mq_open) and older System V (msgget) variants exist.

Shared Memory

The fastest IPC. Both processes attach the same region; after that, communication is just reading and writing memory — no system call per exchange, no copying. The catch: you must coordinate access with semaphores or mutexes (Part V), or you'll get races.

POSIX shared memory (create, map, use)int fd = shm_open("/myshm", O_CREAT | O_RDWR, 0666);  // a named shm object
ftruncate(fd, 4096);                                   // size it to one page
char *mem = mmap(NULL, 4096, PROT_READ | PROT_WRITE,
                 MAP_SHARED, fd, 0);                   // map into address space

strcpy(mem, "written by process A");   // another process mapping /myshm sees this
// ... coordinate with a semaphore so B reads only after A writes ...
munmap(mem, 4096);                          // detach; shm_unlink("/myshm") to remove

Signals

A signal is a lightweight asynchronous notification — a "software interrupt" delivered to a process to tell it an event happened. Signals carry no data payload beyond their number; they interrupt the process, which runs a registered signal handler or takes the default action (often terminate). Examples: SIGINT (Ctrl-C), SIGKILL (force kill, uncatchable), SIGSEGV (bad memory access), SIGCHLD (a child changed state — used to reap zombies, Part II).

Catching Ctrl-C with a signal handler#include <signal.h>
#include <stdio.h>

void handler(int sig) {
    printf("\nCaught signal %d — cleaning up\n", sig);
    _exit(0);
}
int main(void) {
    signal(SIGINT, handler);   // run handler() instead of dying on Ctrl-C
    while (1) pause();          // sleep until a signal arrives
}
⚠Common Mistake
Doing complex work in a signal handler. A handler can fire at any instant, so calling non-async-signal-safe functions (like printf or malloc) from it can deadlock or corrupt state. The safe pattern is to set a volatile sig_atomic_t flag in the handler and do the real work in the main loop.

Sockets

A socket is a bidirectional communication endpoint. Its superpower: the same API works for processes on the same machine (UNIX-domain sockets) and across a network (TCP/UDP sockets). Because they generalize to networking, sockets are the backbone of all client-server software — and they get their own treatment in Part XIII.

Remote Procedure Call (RPC)

RPC makes calling a function on a remote machine look like a local call. A client-side stub serializes ("marshals") the arguments into a message, sends it over the network, the server unmarshals and runs the real function, then returns the result the same way. It hides the network behind an ordinary function-call syntax — the foundation of distributed systems, gRPC, and microservices. (The catch: unlike a local call, an RPC can fail, time out, or run twice — distributed systems must plan for that.)

⚑Interview Tip
"Fastest IPC?" Shared memory — because after setup there's no kernel involvement and no copying; processes read/write memory directly. The trade-off you must mention: it provides no synchronization, so you pair it with semaphores/mutexes. Message passing is slower (data is copied through the kernel) but safer and simpler. Naming that trade-off is the whole answer.
