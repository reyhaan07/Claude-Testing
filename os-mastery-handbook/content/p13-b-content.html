Part XIIINetworking from an OS Perspective

Networking is really just I/O to a very special, very slow device: the network. Everything you learned about system calls, interrupts, DMA, and buffering applies — the socket is the file descriptor, the NIC is the device, and the kernel's network stack is the driver's very elaborate cousin.

The Network Stack

Networking is built in layers, each adding a header and a job. From an OS standpoint the key point is where the boundary between your program and the kernel falls: your application lives at the top; the kernel implements the transport and network layers; the driver and NIC handle the link.

▣Key Concept — encapsulation
As data descends the stack, each layer wraps it in a header: your bytes become a TCP segment (ports, sequence numbers), then an IP packet (source/destination IP), then an Ethernet frame (MAC addresses). The receiver's stack strips them off in reverse. The OS owns the transport and network layers, which is why sending data requires crossing into the kernel.

Sockets and the Socket API

A socket is the OS's abstraction of a network endpoint — and, crucially, it is a file descriptor. Once connected, you read()/write() (or recv/send) a socket just like a file. This unification ("everything is a file descriptor") is why the same select/epoll machinery works for files, pipes, and network connections alike.

A minimal TCP server (the classic five calls)int s = socket(AF_INET, SOCK_STREAM, 0);   // 1. create a TCP socket (an fd)
bind(s, (struct sockaddr*)&addr, sizeof addr); // 2. attach to a port
listen(s, 128);                             // 3. mark it passive; queue up to 128 pending
while (1) {
    int c = accept(s, NULL, NULL);           // 4. block until a client connects; new fd
    char buf[1024];
    int n = recv(c, buf, sizeof buf, 0);      // read the client's request
    send(c, buf, n, 0);                     // echo it back
    close(c);                               // 5. done with this client
}

The client side is socket() then connect(), after which it send/recvs. Each accept() returns a new socket fd dedicated to one client, while the listening socket keeps accepting more.

TCP vs UDP

The two transport protocols the kernel offers through sockets embody a fundamental trade-off: reliability vs speed/overhead.

 TCP (SOCK_STREAM)UDP (SOCK_DGRAM)
ConnectionConnection-oriented (3-way handshake)Connectionless (just send)
ReliabilityGuaranteed, in-order, no duplicatesBest-effort; may lose/reorder
Flow/congestion controlYesNo
Overhead / latencyHigher (ACKs, retransmits, state)Lower — minimal
Data modelByte stream (no message boundaries)Discrete datagrams (boundaries kept)
Use forWeb, files, email, SSH — correctness mattersVideo/voice, gaming, DNS — speed matters
⚠Common Mistake
Expecting TCP to preserve message boundaries. TCP is a byte stream: two send()s of 100 bytes may arrive as one recv() of 200, or as 50+150. Your protocol must delimit messages itself (length prefix or delimiter). UDP does keep boundaries — one sendto = one recvfrom — but may drop or reorder them.

Kernel Networking: NIC, Interrupts, and DMA

Here Part X's I/O machinery does the heavy lifting. When a packet arrives:

  1. The NIC receives the frame off the wire and, via DMA, writes it straight into a kernel receive buffer in RAM — no CPU copying.
  2. The NIC raises an interrupt to tell the CPU "a packet is here."
  3. The driver's interrupt handler does minimal work, then defers the heavy processing (a "bottom half" / softirq) so the interrupt returns fast.
  4. The kernel network stack processes the packet up through IP and TCP (checksums, reassembly, sequencing), placing the payload in the socket's receive buffer.
  5. The waiting process's recv() unblocks and copies the data into the app's buffer.
▣Key Concept — interrupt storms and NAPI
At high packet rates, one interrupt per packet can swamp the CPU (an "interrupt storm"). Real kernels use interrupt coalescing and Linux's NAPI, which switches from interrupts to polling under heavy load — the exact polling-vs-interrupt trade-off from Part X, applied to networking. Each packet is held in a kernel buffer structure (Linux's sk_buff) as it moves through the layers, avoiding repeated copies.

Blocking Sockets, Non-Blocking Sockets, and Scale

A simple server dedicates one thread per connection, each blocked in recv(). That's easy but doesn't scale: 100,000 connections would need 100,000 threads — enormous memory and context-switch overhead. This is the historic C10K problem (handling 10,000+ concurrent connections).

The solution is non-blocking sockets plus an event-notification system call. One (or a few) threads ask the kernel "which of these thousands of sockets are ready?" and service only those:

  • select/poll — portable but O(n): scan all fds each call.
  • epoll (Linux) / kqueue (BSD/macOS) — scalable, O(1)-ish: the kernel keeps the interest list and returns only the ready fds.
  • io_uring (modern Linux) — full asynchronous I/O with shared ring buffers, minimizing system calls entirely.
⚑Interview Tip
"How does a server handle 100k connections?" Not with 100k threads. Use non-blocking sockets + an event loop (epoll): a small thread pool waits on the kernel to report which sockets are readable/writable, then handles just those. This is how nginx, Redis, and Node.js scale. The idea traces straight back to non-blocking + async I/O from Part X — networking is just I/O at scale.
