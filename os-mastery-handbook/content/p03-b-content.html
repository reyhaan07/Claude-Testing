Part IIIThreads & Concurrency

If a process is a running program with its own memory, a thread is a single flow of execution within that memory. Threads let one program keep a UI responsive while it downloads a file, or serve thousands of users at once — but because they share memory, they force us to confront concurrency head-on.

What Is a Thread?

What is it? A thread (short for "thread of execution") is the smallest unit the CPU schedules — a single sequential flow of instructions with its own program counter, registers, and stack, running inside a process and sharing that process's memory and resources with its sibling threads.

Simple intuition. A process is a kitchen; a thread is a cook. One cook (single-threaded) does everything in sequence. Add more cooks (threads) in the same kitchen and they work simultaneously, sharing the same ingredients, counters, and fridge (memory). They get more done — but if two cooks grab the same knife at once, you have a problem (a race condition).

Why do we need it? Before threads, doing two things at once meant two processes, which are expensive to create and cannot easily share data. Threads are lightweight and share memory by default, so a single program can naturally overlap work — compute while waiting on I/O, or spread computation across CPU cores.

Process vs Thread — What's Shared, What's Private

This is the most-asked threading question. The answer hinges on one picture: threads of a process share almost everything, but each keeps its own execution state.

⚠Common Mistake
"Threads have their own heap." No — the heap is shared. If thread A mallocs and passes the pointer to thread B, B can use it. Only the stack is per-thread. This is precisely why passing a pointer to a local (stack) variable of one thread to another thread is dangerous.

Why Threads? (And When Not To)

  • Responsiveness — one thread handles the UI while another does slow work; the app never freezes.
  • Resource sharing — threads share memory for free; no IPC plumbing needed.
  • Economy — creating and switching threads is far cheaper than processes.
  • Scalability / parallelism — on a multi-core CPU, threads run truly simultaneously, one per core, cutting wall-clock time.

The cost: shared memory means shared bugs. Race conditions, deadlocks, and hard-to-reproduce "Heisenbugs" are the price. And more threads is not always faster — see the tip below.

⚑Interview Tip
"Why can too many threads reduce performance?" Because (1) each thread adds context-switching and scheduling overhead; (2) beyond the core count, threads compete for the same cores, so you pay switching cost without gaining parallelism; (3) more threads means more lock contention (they serialize on shared locks) and more cache thrashing. The sweet spot for CPU-bound work is roughly one thread per core; for I/O-bound work you can use more, since threads spend time blocked.

User-Level vs Kernel-Level Threads

Who manages the threads — a user-space library, or the kernel? This choice has real consequences.

User-level threads (ULT)
Managed entirely by a library in user space; the kernel sees only one process and knows nothing of the threads. + Very fast to create/switch (no system call); portable. − If one thread makes a blocking system call, the whole process blocks (the kernel blocks the one process it can see); cannot use multiple cores.
Kernel-level threads (KLT)
Managed by the kernel, which schedules each thread individually. + One thread blocking doesn't stop the others; real parallelism across cores. − Creation and switching involve the kernel, so they're slower than ULTs.

Modern systems (Linux, Windows) use kernel-level threads — every pthread maps to a kernel-scheduled thread — because true multi-core parallelism and non-blocking behavior matter more than the last drop of switch speed.

Multithreading Models

These describe how user threads map onto kernel threads.

Many-to-One

Many user threads map to a single kernel thread. Thread management is cheap and in user space, but one blocking call blocks everyone, and no multi-core parallelism. (Old "green threads.")

One-to-One

Each user thread maps to its own kernel thread. True concurrency and parallelism; a block affects only that thread. Cost: creating many threads creates many kernel threads. This is what Linux and Windows use today.

Many-to-Many

Many user threads multiplexed onto a smaller-or-equal pool of kernel threads. Combines flexibility (create as many user threads as you like) with parallelism (multiple kernel threads). Complex to implement; used by some runtimes (e.g. Go's goroutine scheduler is a modern many-to-many-style design).

Thread Control Block (TCB). Just as a process has a PCB, each thread has a lighter TCB holding its thread ID, register set, program counter, stack pointer, and scheduling state. Threads of one process share the PCB's memory and resource fields but each have their own TCB.

Concurrency vs Parallelism

These two words are used interchangeably in casual speech and must be distinguished precisely in an interview.

▣Key Concept
Concurrency = dealing with many things at once (structure): tasks are in progress over overlapping time periods, possibly interleaved on one core. Parallelism = doing many things at the exact same instant (execution): tasks literally run simultaneously on multiple cores. Concurrency is about how you structure work; parallelism is about how it executes. You can have concurrency on a single core (via interleaving); you need multiple cores for parallelism.

Analogy. A single barista taking one order while steaming milk for another, alternating between them, is concurrent. Two baristas each making a full drink at the same time is parallel.

Multi-Core Systems

A modern CPU packs several cores, each a full processing unit able to run a thread independently. The OS scheduler spreads runnable threads across cores, achieving real parallelism. Some cores support simultaneous multithreading (Intel's Hyper-Threading), presenting two logical CPUs per physical core to better utilize execution units. To software, each logical CPU is just another place to run a thread — which is why one-to-one threading maps so naturally onto modern hardware.

Race Conditions and Critical Sections

The moment two threads share mutable data, correctness is at risk. This section introduces the problem; Part V solves it in full.

Race condition. A race condition occurs when the outcome of a program depends on the timing or interleaving of threads accessing shared data — and at least one is writing. The result is nondeterministic: it might work a thousand times and corrupt data on the thousand-and-first.

The classic race: two threads incrementing a shared counter// counter++ is NOT atomic. The CPU actually does three steps:
//   1) read  counter  into a register
//   2) add   1
//   3) write register back to counter

// If two threads interleave those steps on counter = 5:
//   T1 reads 5 ─┐                     T2 reads 5 ─┐
//   T1 adds → 6 │                     T2 adds → 6 │
//   T1 writes 6 ┘                     T2 writes 6 ┘
// Two increments happened, but counter is 6, not 7. One update was LOST.

Critical section. A critical section is a piece of code that accesses shared data and must not be executed by more than one thread at a time. The fix for a race is to enforce mutual exclusion over the critical section — only one thread inside at once — using a lock, mutex, or semaphore (Part V).

Thread Safety

Code is thread-safe if it behaves correctly when called from multiple threads at once, regardless of interleaving. You achieve it by (a) avoiding shared mutable state (use locals/immutable data), (b) protecting shared state with locks, or (c) using atomic operations. A function that keeps hidden shared state (like the classic strtok) is not thread-safe; reentrant variants (strtok_r) are provided precisely for threaded use.

A minimal POSIX threads (pthreads) program#include <pthread.h>
#include <stdio.h>

void *worker(void *arg) {
    long id = (long)arg;
    printf("thread %ld running\n", id);
    return NULL;
}

int main(void) {
    pthread_t t[4];
    for (long i = 0; i < 4; i++)
        pthread_create(&t[i], NULL, worker, (void *)i);  // spawn
    for (int i = 0; i < 4; i++)
        pthread_join(t[i], NULL);                        // wait for each
    return 0;                 // compile with: gcc prog.c -lpthread
}
