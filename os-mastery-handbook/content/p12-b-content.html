Part XIIStorage Systems

Storage is where the millisecond world of mechanics meets the nanosecond world of the CPU. Because a disk seek is millions of times slower than a memory access, the order in which the OS serves disk requests matters enormously — and RAID is how we make many imperfect disks into one reliable, fast whole.

HDD vs SSD

A Hard Disk Drive (HDD) stores data magnetically on spinning platters. Data sits in concentric tracks, divided into sectors; the same track across stacked platters forms a cylinder. A moving read/write head on an arm must physically reach the data. So an HDD access has three time components:

Access time = seek time (move head to track) + rotational latency (wait for sector to spin under head) + transfer time

Seek time dominates and is mechanical — which is exactly why request ordering (scheduling) can hugely reduce total head movement.

A Solid-State Drive (SSD) stores data in flash memory — no moving parts. Any block is reachable in roughly constant time, so there is no seek or rotational latency. SSDs are far faster (especially for random access), silent, and shock-resistant, but cost more per GB and have limited write-erase cycles (managed by wear leveling).

Disk Scheduling

When several I/O requests are queued for an HDD, the OS chooses the service order to minimize total head movement (and thus seek time). We evaluate algorithms by total head movement across a request queue.

▣Shared example for every algorithm
Request queue (cylinders): 98, 183, 37, 122, 14, 124, 65, 67. Head starts at 53; disk has cylinders 0–199; for directional algorithms the head is moving toward higher numbers.

FCFS — First-Come, First-Served

Serve requests in arrival order. Fair, but the head can whipsaw across the disk.

53→98→183→37→122→14→124→65→67. Movement = 45+85+146+85+108+110+59+2 = 640 cylinders.

SSTF — Shortest Seek Time First

Always serve the closest request to the current head position. Greatly reduces movement, but can starve far-away requests (analogous to SJF).

53→65→67→37→14→98→122→124→183. Movement = 12+2+30+23+84+24+2+59 = 236 cylinders.

SCAN — the Elevator Algorithm

The head sweeps in one direction serving all requests, reaches the end of the disk, then reverses. Like an elevator going all the way up, then all the way down. No starvation; fairer than SSTF.

Moving up: 53→65→67→98→122→124→183→199 (end), then down →37→14. Movement = (199−53) + (199−14) = 146+185 = 331 cylinders.

C-SCAN — Circular SCAN

Like SCAN, but after reaching the end it jumps straight back to the start (0) without servicing on the return, then sweeps up again. This gives more uniform wait times (every cylinder is treated the same way), avoiding SCAN's bias toward the middle.

Up: 53→…→183→199, jump to 0, then 0→14→37. Movement = (199−53) + (199) + (37) = 146+199+37 = 382 cylinders (the 199 is the return sweep).

LOOK and C-LOOK

The practical versions of SCAN/C-SCAN: instead of going all the way to the physical end, the head only goes as far as the last request in that direction, then reverses (LOOK) or jumps back (C-LOOK). Saves the wasted travel to the disk edge.

LOOK: up to 183 (last request), then down to 14. Movement = (183−53) + (183−14) = 130+169 = 299.   C-LOOK: up to 183, jump to 14, up to 37. Movement = 130 + 169 + 23 = 322.

⚠Common Mistake
Forgetting to state the initial direction and whether the algorithm goes to the physical end (SCAN/C-SCAN) or only to the last request (LOOK/C-LOOK). The same queue gives different totals depending on both. Always write down the head's starting position and direction before you begin.

RAID — Redundant Array of Independent Disks

RAID combines multiple physical disks into one logical unit for performance (spread I/O across disks), redundancy (survive disk failures), or both. The two building blocks:

Striping
Split data across disks so reads/writes happen in parallel → speed. No redundancy by itself.
Mirroring / Parity
Store redundant information (a full copy, or parity bits) so a failed disk's data can be reconstructed → fault tolerance.

▣Key Concept — how parity recovers data
RAID 5 stores parity = the XOR of the data blocks in a stripe. If one disk dies, its block is recomputed as the XOR of the survivors (X ⊕ parity = the missing block). That's why RAID 5 needs only one extra disk's worth of space to tolerate one failure. RAID 6 adds a second, independent parity so it can lose two disks. The cost is the write penalty: every write must also update parity (read-modify-write).
⚑Interview Tip
"RAID 0 vs 1 vs 5 vs 10?" Compress it: 0 = speed, no safety; 1 = safety via a full copy; 5 = efficient safety via parity (survives 1); 6 = survives 2; 10 = speed + safety, at 50% capacity. And the trap: RAID is not a backup — it protects against disk failure, not against deletion, corruption, ransomware, or fire. You still need real backups.

⚑Practical Task
On Linux, run lsblk to list your storage devices and cat /sys/block/sda/queue/scheduler to see (and, as root, change) the kernel's active I/O scheduler (e.g. mq-deadline, none for SSDs). Note that SSDs often use none — confirming scheduling matters less without seeks.
