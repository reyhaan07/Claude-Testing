Part IXFile Systems

The file is the OS's most successful abstraction — so natural you forget it's an illusion. Underneath, the file system maps names to inodes, inodes to disk blocks, and turns a raw array of sectors into the durable, named, permissioned storage every program relies on.

Files and Their Attributes

A file is a named collection of related information stored on secondary storage — the logical unit the OS presents to users. To the OS a file is just a sequence of bytes (in UNIX; other systems impose record structure). Each file carries metadata — its attributes:

  • Name — human-readable identifier (in the directory, not the inode).
  • Type — regular file, directory, symlink, device, etc.
  • Size, location (which disk blocks), timestamps (created, modified, accessed).
  • Owner & permissions — who may read/write/execute.

File Operations (and the system calls behind them)

The OS exposes files through a small set of operations, each backed by a system call: create, open, read, write, seek (move the read/write position), close, delete (unlink). We trace open…close in detail in §9.7.

Directories

A directory (folder) is itself a special file whose contents are a table mapping names → inode numbers. That's the crucial insight: a directory doesn't "contain" files — it contains names that point to inodes. This is exactly why one file can have several names (hard links, §9.6). Directories nest to form the familiar tree, rooted at / on UNIX.

Inodes — the Heart of a UNIX File System

What is it? An inode (index node) is the on-disk data structure that stores everything about a file except its name and its data: the file's metadata plus pointers to the disk blocks holding its contents. Every file has exactly one inode, identified by an inode number.

▣Key Concept
Name and content are decoupled: the directory holds the name→inode mapping; the inode holds metadata + block pointers; the data blocks hold the bytes. This three-way split explains hard links (many names, one inode), why renaming a file is instant (just edit a directory entry), and why "deleting" a file really means dropping a directory entry and decrementing the inode's link count.

File Allocation Methods

How are a file's data blocks arranged on disk? Three classic strategies, each a trade-off between sequential-access speed, random-access speed, and fragmentation.

MethodHow+ Pros− Cons
ContiguousFile occupies consecutive blocks; store start + lengthFast sequential & random access; simpleExternal fragmentation; hard to grow a file
LinkedEach block stores a pointer to the next (a linked list on disk)No external fragmentation; files grow easilyNo random access (must walk); pointer overhead; a bad pointer loses the rest
IndexedAn index block holds all the file's block pointersFast random access; no external fragmentationIndex block overhead for small files; max size limited by index size

The inode scheme (§9.3) is indexed allocation made scalable: a few direct pointers for small files, plus single/double/triple indirect blocks so a small inode can still address a very large file. This is why UNIX file systems handle both tiny and huge files efficiently.

Free-Space Management

The FS must track which blocks are free. Two common methods:

  • Bitmap (bit vector) — one bit per block: 1 = free, 0 = used. Easy to find contiguous runs; compact. Used widely.
  • Free list — link all free blocks together. Space-efficient but slow to find contiguous space.

Hard Links vs Symbolic (Soft) Links

Both give a file more than one name, but very differently — a classic interview distinction.

Hard link
A directory entry pointing to the same inode as the original. The file has two equal names; there's no "original." The inode's link count tracks how many names point to it; the data is freed only when the count hits 0. Cannot span file systems (inode numbers are per-FS) and cannot link directories.
Symbolic (soft) link
A tiny special file whose contents are a path to another file — a pointer by name. Like a shortcut. Can cross file systems and link directories, but breaks if the target is moved or deleted (a "dangling" link).

The Life of open / read / write / close

This is where files and the kernel meet, and it's a favorite "explain what happens" question. Three kernel tables cooperate:

  1. Per-process file descriptor table — small integer FDs (0=stdin, 1=stdout, 2=stderr, then 3,4…) map to entries in…
  2. System-wide open-file table — one entry per open(), holding the current file offset and mode, pointing to…
  3. In-memory inode table — the actual file (metadata + block pointers).
Reading a file with raw system callsint fd = open("data.txt", O_RDONLY);   // returns smallest free fd, e.g. 3
char buf[256];
ssize_t n = read(fd, buf, sizeof buf);  // copy up to 256 bytes; advance offset by n
// ... use buf ...
close(fd);                              // release the fd and open-file entry

What the kernel does on open: resolve the path (walk directories to find the inode), check permissions, allocate an open-file-table entry (offset 0), install a descriptor in the process's fd table, and return that integer. read uses the offset to find the right blocks (via the inode), copies data from the buffer cache (loading from disk on a miss), and advances the offset. close tears down the descriptor.

Mounting, Journaling, and Consistency

Mounting
Attaching a file system (on a disk/partition/USB) into the existing directory tree at a mount point (a directory). After mount /dev/sdb1 /mnt, the device's files appear under /mnt. This is how UNIX unifies many devices into one tree with no drive letters.
File-system consistency
A crash mid-update can leave the FS inconsistent (e.g. a block marked used in the inode but free in the bitmap). Old systems ran a slow full scan (fsck) to repair after a crash.
Journaling
The modern fix. Before modifying the FS, write the intended changes to a journal (log); then apply them. After a crash, the OS just replays (or discards) the journal — fast and safe, no full scan. ext4, NTFS, and XFS are journaling file systems.
▣Key Concept — why journaling works
The danger is a crash between two related updates leaving the FS half-changed. Journaling makes the multi-step update atomic-ish: either the journal entry is complete (and gets replayed) or it isn't (and gets ignored), so the FS is never left in a torn state. It's the same write-ahead-log idea databases use for durability.

Linux File System Basics

Everything in UNIX is a file — regular files, directories, devices (/dev/sda), even kernel state (/proc, /sys — Part XIV). The Virtual File System (VFS) is a kernel abstraction layer so the same open/read/write calls work across ext4, FAT, NFS, etc. File permissions use three classes (owner, group, other) × three rights (read, write, execute), shown as rwxr-xr-- and set with chmod (Part XIV).
