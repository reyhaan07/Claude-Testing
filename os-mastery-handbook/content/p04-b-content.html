Part IVCPU Scheduling

CPU scheduling is where operating-systems theory becomes arithmetic you can be tested on. This part teaches every classic algorithm the way an interviewer or examiner wants it: the intuition, the mechanism, a Gantt chart, and the full turnaround/waiting-time calculation worked to the last number.

Why CPU Scheduling? The Metrics

A process alternates CPU bursts with I/O bursts (Part II). While one process waits on I/O, the CPU would sit idle — a waste. The scheduler keeps the CPU busy by picking another Ready process to run. The dispatcher is the component that actually performs the context switch to hand the CPU over. The rules the scheduler follows are the scheduling algorithm, and we judge algorithms by these metrics:

Arrival Time (AT)When the process enters the ready queue— (given)

Completion Time (CT)When the process finishes— (computed)
Turnaround TimeTAT = CT − AT (total time in system)Minimize

▣Key Concept — the three formulas that solve every problem
Turnaround Time = Completion Time − Arrival Time
Waiting Time = Turnaround Time − Burst Time
Response Time = First-CPU Time − Arrival Time
Build the Gantt chart first, read off each Completion Time, then apply these. Every numerical in this part — and in your exam — is just these three lines applied carefully.

Two problems to watch for

Starvation
A process waits indefinitely because others keep being preferred (common with priority and SJF, where a low-priority or long job may never get picked).
Convoy effect
Short processes stuck waiting behind one long process (classic FCFS problem), tanking average waiting time — like a line of cars stuck behind one slow truck.

Modern general-purpose OSes are preemptive — essential for interactivity and to stop any one process from hogging the CPU.

⚠Common Mistake
Forgetting idle time. If no process has arrived yet, the CPU sits idle and the timeline still advances. E.g. if P1 arrives at t=3 with nothing before it, the Gantt starts with idle [0→3], and P1's completion is 3+BT, not BT.

SJF — Shortest Job First (Non-Preemptive)

Intuition. Always run the Ready process with the smallest CPU burst next. Clearing the quick jobs first drags the average waiting time down. SJF is provably optimal for minimum average waiting time — among non-preemptive algorithms, no policy beats it.

Worked example (all arrive at t=0 for clarity): P1 BT=6, P2 BT=8, P3 BT=7, P4 BT=3. Pick shortest first: P4(3), P1(6), P3(7), P2(8).

SRTF — Shortest Remaining Time First (Preemptive SJF)

Intuition. The preemptive version of SJF: whenever a new process arrives, compare its burst against the remaining time of the running process; if the newcomer is shorter, preempt. Decisions are re-made at every arrival.

Worked example: P1(AT=0,BT=8), P2(AT=1,BT=4), P3(AT=2,BT=9), P4(AT=3,BT=5).

  • t=0: only P1 → run P1.
  • t=1: P2(4) arrives; P1 remaining=7. 4<7 → preempt, run P2.
  • t=2,3: P3(9), P4(5) arrive; P2 remaining (3, then 2) still smallest → keep P2.
  • t=5: P2 done. Remaining P1=7, P3=9, P4=5 → run P4 (5).
  • t=10: P4 done. Remaining P1=7, P3=9 → run P1 (7).
  • t=17: P1 done. Run P3 (9) → done at 26.

Priority Scheduling

Intuition. Each process has a priority number; the CPU always goes to the highest-priority Ready process. (Convention here: smaller number = higher priority.) Can be preemptive or non-preemptive. SJF is actually priority scheduling with priority = 1/burst.

Worked example (non-preemptive, all AT=0): P1(BT=4,pri=3), P2(BT=3,pri=1), P3(BT=1,pri=4), P4(BT=5,pri=2). Order by priority: P2, P4, P1, P3.

▣Key Concept — Starvation & Aging
Priority scheduling can starve low-priority processes forever if high-priority ones keep arriving. The standard cure is aging: gradually raise the priority of a process the longer it waits, so every process eventually becomes high-priority enough to run. (Legend: when MIT's IBM 7094 was shut down in 1973, a low-priority job submitted in 1967 was found still waiting.)

Round Robin (RR)

Intuition. FCFS with a stopwatch. Each process gets a fixed time quantum (time slice); if it doesn't finish, it's preempted and sent to the back of the ready queue. Designed for fairness and good response time — the heart of interactive time-sharing.

⚑Interview Tip — choosing the quantum
The time quantum is a knob. Too large → RR degenerates into FCFS (each job finishes in one slice), hurting response time. Too small → excessive context-switch overhead eats the CPU. Rule of thumb: the quantum should be large enough that ~80% of CPU bursts finish within it, typically 10–100 ms. RR optimizes response time and fairness, not average waiting time.

Multilevel Queue (MLQ)

Real systems have different classes of process (interactive, batch, system). MLQ splits the ready queue into several separate queues, each with its own scheduling algorithm, and processes are permanently assigned to one queue by type.

− Rigid — a process is stuck in its queue, and low queues can starve. That rigidity motivates the next algorithm.

Multilevel Feedback Queue (MLFQ)

The most sophisticated classic scheduler, and the closest to what real OSes use. Like MLQ, but processes can move between queues based on observed behavior:

  • New processes enter the top (highest-priority, short-quantum) queue.
  • A process that uses its whole quantum (CPU-bound) is demoted to a lower, longer-quantum queue.
  • A process that yields early for I/O (interactive) stays high or is promoted.
  • Periodic aging boosts long-waiting processes to prevent starvation.
▣Key Concept
MLFQ learns each process's nature without being told its burst time: interactive jobs (short bursts) naturally float to the top for great responsiveness, while CPU hogs sink to the bottom where they run efficiently in long slices. It approximates SJF's benefits without needing to know burst times in advance. This is why it's the design basis for Windows, macOS, and older Linux schedulers.

Real-world: Linux's modern CFS (Completely Fair Scheduler) doesn't use fixed slices at all — it tracks each task's "virtual runtime" and always runs the one that has had the least CPU, approximating perfect fairness. The classic algorithms above remain the vocabulary for reasoning about and interviewing on scheduling.
