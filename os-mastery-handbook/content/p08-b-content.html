Part VIIIVirtual Memory

Paging (Part VII) let a process's memory be scattered across frames. Virtual memory takes the next leap: a page need not be in RAM at all. Keep only the pages a process is actively using in memory and park the rest on disk, and suddenly the machine can run far more than fits.

What Is Virtual Memory, and Why?

What is it? Virtual memory is a technique that lets a process execute even when only part of it is in physical RAM; the rest lives on disk (in the swap area or the program file) and is brought in on demand. Each process gets a large virtual address space independent of how much RAM exists.

Why? (1) Programs can be larger than physical memory. (2) More processes fit in RAM at once (only their active pages are resident), raising CPU utilization and multiprogramming. (3) Less I/O to load a program — start running before it's fully loaded. (4) It cleanly enables per-process isolation and features like copy-on-write and memory-mapped files.

▣Key Concept
Virtual memory works because programs exhibit locality of reference: at any moment a process touches only a small subset of its pages (its working set). Keep that hot subset in RAM and almost every access is a fast hit; the cold majority can sit on disk unnoticed.

Demand Paging

Demand paging is the usual implementation: don't load a page until it's actually referenced ("load on demand"). Each page-table entry has a valid/invalid (present) bit. When a page is in RAM the bit says "valid" and translation proceeds normally. When the page is on disk the bit says "invalid," and touching it triggers a page fault.

Page Faults and Their Handling

A page fault is the exception raised when a process references a page that is not currently in RAM. It is not an error — it's the normal signal that the OS must fetch the page. Handling it:

Cost. A page fault is enormously expensive — a disk read is ~105–106× slower than a RAM access. So the effective access time is dominated by the fault rate:

EAT = (1 − p) × memory_access + p × page_fault_time

With memory access 100 ns and a page fault costing 8 ms (8,000,000 ns), even a fault probability of p = 0.001 gives EAT ≈ 100 + 0.001×8,000,000 = 8100 ns — 81× slower. This is why keeping the fault rate tiny (via good replacement and enough RAM) is everything.

Page Replacement Algorithms

When a page fault occurs and no frame is free, the OS must evict a resident page to make room. Which one? A good choice minimizes future faults. We measure algorithms by counting page faults on a reference string (the sequence of page numbers a process touches).

Shared example. Reference string 1 2 3 4 1 2 5 1 2 3 4 5, 3 frames.

FIFO — First-In, First-Out

Evict the page that has been in memory longest (oldest arrival). Simple; uses a queue. But "oldest" isn't "least useful," so it can evict a hot page.

Optimal (OPT / MIN)

Evict the page that will not be used for the longest time in the future. Provably the best possible — the fewest faults of any algorithm. It's unimplementable (needs the future), but it's the gold standard we compare against. On the same string, OPT gives 7 faults.

LRU — Least Recently Used

Evict the page not used for the longest time in the past. A practical approximation of Optimal, banking on locality (the recent past predicts the near future). Costly to implement exactly (needs a timestamp or ordering per access). On the same string, LRU gives 10 faults here.

Clock (Second-Chance)

A cheap LRU approximation used in real kernels. Frames sit in a circular list; each has a reference bit set on use. A "clock hand" sweeps: if the bit is 1, clear it and give the page a "second chance" (skip it); if 0, evict it. It approximates LRU with just one bit and no per-access bookkeeping.

▣Key Concept — Belady's Anomaly
Intuitively, more frames should mean fewer faults. For FIFO, that can fail: on the string 1 2 3 4 1 2 5 1 2 3 4 5, FIFO gives 9 faults with 3 frames but 10 faults with 4 frames — more memory, more faults! This is Belady's anomaly. It afflicts FIFO but never stack algorithms like LRU and Optimal (which guarantee the set of pages with k frames is always a subset of the set with k+1 frames).

Thrashing, Working Set, and Locality

Locality of reference is the empirical fact that processes access a small, slowly-changing set of pages at a time (loops reuse the same code; arrays are walked in order). Two flavors: temporal (a byte used now is likely used again soon) and spatial (nearby bytes are likely used soon). Locality is why caches and virtual memory work at all.

The working set of a process is the set of pages it has referenced in the recent time window — essentially its current locality. If RAM can hold every process's working set, fault rates stay low. If it can't…

▣Key Concept — Thrashing
Thrashing is when a system spends more time paging (swapping pages in and out) than executing. It happens when the combined working sets exceed physical memory: every process constantly faults, evicting a page another process needs immediately, which faults again. CPU utilization collapses even though the CPU looks "busy" — busy doing I/O for paging. The fixes: reduce the multiprogramming level (run fewer processes), add RAM, or use the working-set model/page-fault-frequency control to give each process enough frames.

Copy-on-Write (COW)

What & why. Recall fork() (Part II) logically copies the parent's entire address space — wasteful, since the child often calls exec() immediately and discards it. Copy-on-write avoids the copy: parent and child share the same physical pages, marked read-only. As long as both only read, they share. The instant either writes a shared page, the MMU traps, and the OS makes a private copy of just that one page for the writer. Copying is deferred until (and only for pages) actually modified.

COW makes fork() nearly free and is used well beyond it — e.g. loading the same shared library into many processes without duplicating it in RAM.

Memory-Mapped Files

What. Instead of read()/write() system calls, a process can mmap() a file directly into its virtual address space, so the file appears as an array in memory. Accessing address ptr[i] reads byte i of the file; the OS demand-pages file contents in as you touch them and writes dirty pages back. Why: it avoids explicit I/O calls and extra copying, and it lets multiple processes share the same file pages in memory (the basis of shared memory IPC — Part XI, and of how executables/libraries load).
