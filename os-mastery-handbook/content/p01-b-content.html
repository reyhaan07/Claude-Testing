Part IOS Fundamentals & Architecture

A modern computer is a pile of extraordinarily fast but extraordinarily literal hardware. The operating system is the layer of software that turns that raw hardware into something a human — and a program — can actually use safely. This part builds the mental model that every later part depends on.

What Is an Operating System?

What is it? An operating system (OS) is the master program that sits between your applications and the physical hardware. It controls the hardware and provides services that every program can use, so that programs never have to talk to the raw metal directly.

Why do we need it? Imagine writing a program that plays a sound. Without an OS you would have to know the exact model of sound card, write the precise byte sequences it expects, manage the electrical timing, and make sure no other program touches the card at the same time. Now do that again for every keyboard, disk, network card, and GPU ever made. It is hopeless. The OS solves this once, for everyone, and hands you a simple request like "play these bytes."

▣Key Concept
An operating system does two big jobs at once: it is a resource manager (it decides who gets the CPU, memory, and devices, and when) and an extended machine / abstraction layer (it hides ugly hardware details behind clean, uniform interfaces like files and processes).

Simple intuition. Think of an OS as the manager of a busy shared workshop. Many workers (programs) want the same tools (CPU, memory, printer). The manager hands out tools fairly, stops two workers from grabbing the same tool at once, cleans up when a worker leaves, and gives everyone the same simple checkout process instead of making each worker learn how every tool is wired internally.

Technical explanation. The OS is a collection of software — centered on the kernel — that (1) manages hardware resources (processor time, memory, storage, I/O devices), (2) provides an execution environment for programs called the process, (3) exposes services through system calls, and (4) enforces protection so a fault or attack in one program cannot corrupt another or the OS itself.

How it works internally. The OS is loaded into memory at boot and stays resident. It runs in a privileged CPU mode so it can execute instructions ordinary programs cannot. When a program needs something only the OS can do (read a file, get more memory, send a packet), it makes a controlled request that switches the CPU into the OS, the OS does the work, and control returns to the program. Between those requests, the OS is mostly idle — it is event-driven, woken by system calls and hardware interrupts.

Example. When you run ls in a terminal, the OS finds the program on disk, loads it into memory, gives it CPU time, lets it ask the file system for directory contents, sends its output to your terminal, and reclaims its memory when it exits — all without ls knowing anything about your specific SSD or display.

Real-world example. Linux, Windows, macOS, Android, and iOS are operating systems. The same Chrome browser binary logic runs on wildly different laptops because the OS hides those differences. Your phone runs dozens of apps on one CPU because the OS shares it among them.

Related concepts. Kernel (§1.4), system calls (§1.7), processes (Part II), and protection (§1.10) are all facets of these two core jobs.

⚠Common Mistake
"The OS is the desktop, windows, and icons." That graphical shell is just one application running on top of the OS. You can run Linux with no graphics at all. The OS is the kernel and its services — the part that manages the hardware — not the wallpaper.
⚑Interview Tip
Asked "What is an operating system?", give the two-job answer in one breath: "It's the software that manages hardware resources and provides an abstraction layer so programs can use the hardware safely and portably through a uniform interface." Then be ready to expand either half.

Resource Manager & Extended Machine

These are the two classic lenses for understanding everything an OS does. Every feature in this book is one or the other (usually both).

The OS as a Resource Manager

The hardware has finite resources; many programs want them simultaneously. The OS multiplexes them — in time (the CPU runs process A for a few milliseconds, then B, then C, so fast it looks simultaneous) and in space (RAM is divided so each process gets its own region). It must do this fairly (no program starves), efficiently (little overhead), and safely (one program cannot read or wreck another's resources).

The OS as an Extended (Virtual) Machine

Raw hardware is hostile to program: disks store numbered blocks, not "files"; memory is one flat array shared by all; the CPU has no notion of "a program." The OS presents a friendlier extended machine where those hard things become easy abstractions:

Ugly hardware realityClean OS abstraction
Numbered disk sectors, no namesFiles and directories with names
One shared physical RAMA private virtual address space per program
One CPU, one instruction streamMany concurrent processes and threads
Device-specific register pokesUniform read()/write() calls
▣Key Concept
Abstraction = hiding complexity behind a simpler interface. Virtualization = giving each program the illusion it has the whole machine to itself. The OS does both constantly: a file is an abstraction of disk blocks; a process is a virtualization of the CPU; virtual memory is a virtualization of RAM.

Hardware, OS, and Application: The Layered View

The single most useful picture in this book. Memorize it — nearly every question about "what happens when…" is really a question about how a request travels down and back up these layers.

The two horizontal lines that matter most are: the API boundary (between your app and the library) and the system-call boundary (between user space and the kernel). The second is the famous "user/kernel line," and crossing it is not free — see §1.7.

Kernel, User Space, and Kernel Space

What is the kernel? The kernel is the core of the OS — the part that is always in memory, runs with full hardware privilege, and directly manages processes, memory, and devices. When people say "the OS did X," they usually mean the kernel did X.

Memory is conceptually split into two territories:

Kernel space
The memory region where the kernel's code and data live. Only privileged (kernel-mode) code may access it. Protected from ordinary programs.
User space
Where ordinary programs (and their libraries) run. Each process gets its own user-space view. Code here cannot touch kernel space or other processes' memory directly.
▣Key Concept
User space vs kernel space is about memory and privilege territory. User mode vs kernel mode (next section) is about the CPU's current privilege state. They move together: code in user space runs in user mode; the kernel runs in kernel mode. Do not confuse the two axes — one is "where the memory is," the other is "what the CPU is allowed to do right now."

Dual-Mode Operation: User Mode and Kernel Mode

Why do we need it? If every program could run any instruction and touch any memory, one buggy or malicious program could halt the CPU, erase the disk, or read your passwords out of another program. To prevent that, the CPU itself supports (at least) two privilege levels.

Kernel mode (supervisor / privileged mode)
The CPU can execute every instruction and access all memory and devices. The kernel runs here.
User mode
A restricted state. Privileged instructions are forbidden; memory access is limited to the process's own space. Applications run here.

How it works internally. A bit in a CPU register (the "mode bit," e.g. current privilege level / ring on x86) records the mode. In user mode, if a program attempts a privileged instruction or touches memory it does not own, the hardware immediately raises an exception (trap) and jumps into the kernel, which typically kills the offending program (the classic segmentation fault). The only legitimate ways to get from user mode into kernel mode are a system call, an interrupt, or an exception — all of which enter the kernel at fixed, trusted entry points. A program can never simply "switch itself" to kernel mode; that is the whole point.

⚠Common Mistake
Thinking a program "calls the kernel like a normal function." It does not — a normal call cannot change privilege. A system call executes a special CPU instruction (e.g. syscall on x86-64) that atomically switches to kernel mode and jumps to a fixed kernel entry point. That hardware-enforced doorway is what makes the boundary safe.

Privileged Instructions

A privileged instruction is a machine instruction that can only be executed in kernel mode. These are exactly the operations that could compromise the whole system if any program could run them:

  • Halting the CPU, disabling/enabling interrupts.
  • Loading the page-table base register / switching address spaces (controlling the MMU).
  • Direct access to I/O device registers.
  • Modifying the mode bit or system control registers.
  • Executing hlt, setting timers, flushing the TLB.

Attempting any of these in user mode raises a trap. This single mechanism — "some instructions are off-limits unless you are the kernel" — is the hardware foundation of all OS protection.

System Calls — and API vs System Call

What is it? A system call is the controlled mechanism by which a user-mode program requests a service from the kernel. It is the only door through which a program can ask the OS to do something privileged (open a file, allocate memory, create a process, send data on the network).

Simple intuition. You (a program) cannot walk into the bank vault (hardware). You slide a request form through a small, guarded window (the system call). A teller (the kernel) verifies your request, does it on your behalf, and slides the result back. You never touch the vault yourself.

How it works internally (x86-64 Linux, step by step):

  1. The program puts the system-call number in a register (e.g. rax) and arguments in others (rdi, rsi, rdx…).
  2. It executes the syscall instruction. The CPU switches to kernel mode and jumps to a fixed kernel entry point (the system-call handler).
  3. The kernel looks up the number in the system-call table, validates the arguments, and runs the corresponding kernel function.
  4. The result is placed in a register; the kernel executes a return-from-kernel instruction that switches back to user mode and resumes the program right after the syscall.
A raw system call vs. the library wrapper (Linux, C)/* The C library gives you a friendly wrapper... */
ssize_t n = write(1, "hi\n", 3);   // fd 1 = stdout, 3 bytes

/* ...which internally does roughly this (conceptually): */
//   mov rax, 1        ; syscall number for write on x86-64
//   mov rdi, 1        ; arg1: file descriptor
//   mov rsi, buf      ; arg2: pointer to data
//   mov rdx, 3        ; arg3: byte count
//   syscall           ; <-- traps into the kernel
▣Key Concept — API vs System Call
An API (Application Programming Interface) is the set of functions your code calls, such as the C library's fopen(), printf(), malloc(). A system call is the kernel entry underneath, such as open, write, mmap. Many API functions wrap one or more system calls — but not always: strlen() makes zero system calls, and one printf() may buffer many prints into a single write. The API is what you program against; the system call is what actually crosses into the kernel.

Categories of system calls. Process control (fork, execve, exit, wait), file management (open, read, write, close), device management (ioctl), information (getpid, time), communication (pipe, socket, shmget), and protection (chmod, setuid).

⚑Interview Tip
"Why are system calls expensive?" Because each one costs a mode switch (save user state, switch to kernel mode, run the handler, restore state) plus the kernel's own validation and work, and it can pollute CPU caches and pipelines. That is why libraries buffer — one big write beats a thousand tiny ones. This is also why high-performance systems batch I/O (writev, io_uring) to amortize the crossing.
⚑Real World
Run strace ls on Linux. You will see the actual stream of system calls ls makes — openat, read, write, close, mmap. This is the single best way to see the user/kernel boundary in action. We use it throughout Part XIV.

Traps, Interrupts, and Exceptions

All three are ways the CPU stops what it is doing and jumps into the kernel. Interviewers love the distinction because candidates blur it. Here is the clean version:

TermSourceTimingMeaning & example
InterruptExternal hardware (device)Asynchronous A device signals it needs attention, unrelated to the current instruction. E.g. keyboard press, packet arrival, disk finished, timer tick.
Exception / FaultThe running instruction (CPU)Synchronous The current instruction did something the CPU can't complete. E.g. divide-by-zero, invalid memory access, page fault.
TrapA deliberate instructionSynchronous The program intentionally asks to enter the kernel. E.g. a system call, a debugger breakpoint. (A "software interrupt.")
▣Key Concept
Asynchronous vs synchronous is the crisp dividing line. An interrupt is asynchronous — it comes from the outside world and can arrive between any two instructions. An exception and a trap are synchronous — they are caused by the instruction currently executing. A trap is the intentional kind of exception ("I meant to do that"); a fault is the unintended kind ("something went wrong").

How the kernel responds. The CPU consults the interrupt vector table (a table of handler addresses indexed by interrupt/exception number), saves the current state, switches to kernel mode, and runs the matching interrupt/exception handler. When the handler finishes, the CPU restores state and resumes — either the interrupted program (for an interrupt) or, for a fault it fixed (like a page fault), re-runs the faulting instruction.

OS Services

Everything the OS offers falls into a handful of service categories. You have now met the mechanisms; these are the user-facing results.

  • Program execution — load, run, and end programs (Part II).
  • I/O operations — read/write files and devices without touching hardware (Part X).
  • File-system manipulation — create, delete, search, and protect files (Part IX).
  • Communication — let processes exchange data locally or over a network (Parts XI, XIII).
  • Error detection — catch hardware and software faults and respond safely.
  • Resource allocation — share CPU, memory, and devices among many programs (Parts IV, VII).
  • Accounting & logging — track who used what.
  • Protection & security — isolate programs and users (§1.10).

Protection and Security

These words are related but not identical, and mixing them up is a classic slip.

Protection
Controlling access by programs and users to the resources inside the system — e.g. stopping process A from reading process B's memory, or a user from deleting another user's files. It guards against accidents and internal misuse.
Security
Defending the system against external threats — malware, network attackers, stolen credentials. It guards against deliberate, often external, attacks.

Mechanisms include dual-mode operation, memory protection via the MMU (Part VII), user/group permissions (Part IX), and modern additions like ASLR and namespaces (Part XV). Protection is the foundation; security is built on top of it.

The Boot Process

The chicken-and-egg problem: the OS manages the hardware, but the OS is a program that must itself be loaded and run by the hardware. Booting (from "bootstrapping" — pulling yourself up by your bootstraps) is how the machine climbs from bare power-on to a running OS.

The detail-by-detail version — including what the firmware, bootloader, and PID 1 each do — is in Part XVI, "What happens when I turn on my computer?" For now, the shape is enough: firmware → bootloader → kernel → init → your login.

OS Architectures: Monolithic, Micro, Hybrid, Modular

Where should all this OS code live — one giant privileged blob, or many small pieces? This design choice defines an OS's architecture, and it is a favorite interview and exam topic.

Monolithic Kernel

The entire OS — scheduling, memory, file systems, drivers, network stack — runs together in kernel space as one large program. Components call each other directly as fast function calls.

+ Very fast (no crossing between components). − Huge, complex; a bug in any driver can crash the whole kernel; hard to maintain in isolation. Examples: classic UNIX, Linux (though modular), BSD.

Microkernel

Keep the kernel tiny: only the bare essentials (scheduling, basic memory, and inter-process messaging) run in kernel mode. Everything else — file systems, drivers, networking — runs as ordinary user-space servers that talk via message passing.

+ Robust and secure (a crashed driver doesn't take down the kernel; just restart the server); modular; easier to verify. − Slower — lots of message passing and mode switches. Examples: Minix, QNX, seL4, the Mach core.

Hybrid Kernel

A pragmatic middle ground: a mostly-monolithic kernel for speed, but structured with some microkernel ideas and message passing. Examples: Windows NT, macOS (XNU = Mach + BSD).

Modular Kernel

A monolithic core that can load and unload components at runtime as modules — you get monolithic speed with some of the flexibility of a microkernel. Example: Linux, via loadable kernel modules (a driver you insmod/modprobe without recompiling the kernel; see Part XV). Modern Linux is best described as a modular monolithic kernel.

Saying "Linux is a pure monolithic kernel." It is monolithic in that services run in kernel space, but it is modular — drivers and features load and unload at runtime as kernel modules. The precise answer is "modular monolithic," and saying so signals real understanding.
