Part XIVLinux Practical OS

You can read about processes and page faults forever, but nothing cements them like watching them happen. Every command here is a window onto a concept from earlier parts. Type them. Break things. The kernel is right there, and Linux lets you look inside it.

Watching Processes: ps, top, htop

CommandWhat it doesOS concept it shows
psSnapshot of current processes (PID, state, CPU, memory, command)Processes, PCB fields, process states (Part II)
topLive, updating view of processes and system loadScheduling, CPU/memory sharing, states (Parts II, IV)
htopFriendlier interactive top (per-core bars, tree view, scroll)Multi-core, process tree, priorities (Parts III, IV)
 
Example: see every process with full detail$ ps aux
USER   PID %CPU %MEM   VSZ   RSS STAT  COMMAND
root     1  0.0  0.1 16942  9120 Ss    /sbin/init      # PID 1 = init/systemd
user  2413 12.0  3.4  ...   ...  R     firefox         # R = Running/Runnable
user  2610  0.0  0.1  ...   ...  S     bash            # S = Sleeping (Waiting)
user  3001  0.0  0.0     0     0 Z     <defunct>       # Z = Zombie! (Part II)

The STAT column is the process state from Part II made visible: R runnable, S interruptible sleep (waiting), D uninterruptible sleep (usually disk I/O), Z zombie, T stopped. VSZ is virtual memory size, RSS is resident (physical) memory — the virtual vs physical distinction from Part VII, right there.

Controlling Processes: kill, nice, renice

CommandWhat it doesOS concept it shows
killSend a signal to a process (default SIGTERM)Signals as IPC (Part XI), process termination
niceStart a process with a given scheduling priorityPriority scheduling (Part IV)
reniceChange the priority of a running processDynamic priority, dispatcher (Part IV)
 
Signals and priorities in action$ kill 2413            # polite SIGTERM: "please exit"
$ kill -9 2413         # SIGKILL: force-kill, cannot be caught (Part XI)
$ kill -SIGSTOP 2413   # pause it (→ state T);  kill -SIGCONT resumes

$ nice -n 19 ./batch   # lowest priority (19 = nicest, yields CPU to others)
$ sudo renice -5 -p 2413   # raise firefox's priority (negative = higher)
▣Key Concept — the nice value
Linux "niceness" ranges from −20 (highest priority, least nice) to +19 (lowest priority, nicest). A "nicer" process yields the CPU to others. This is your hands-on control over the priority scheduler from Part IV — set a CPU-hungry backup job to nice 19 and it won't disturb your interactive work.

Job Control: jobs, fg, bg

The shell manages the processes it launches as jobs. This is process control and terminal sessions in miniature.

CommandWhat it does
Ctrl-ZSuspend the foreground job (sends SIGTSTP → state T)
bgResume the suspended job in the background (keeps running, frees your prompt)
fgBring a background job back to the foreground
jobsList the shell's jobs and their states
&Start a command directly in the background: ./server &

Open Files: lsof

lsof ("list open files") reveals every file descriptor every process holds — and since in UNIX everything is a file, that includes regular files, sockets, pipes, and devices. It makes the fd tables from Part IX tangible.

What has this file/port open?$ lsof /var/log/syslog     # which processes hold this file open?
$ lsof -i :8080            # which process is listening on port 8080? (sockets = fds)
$ lsof -p 2413             # every fd process 2413 has open

Memory & Disk: free, df, du

CommandWhat it doesOS concept
free -hPhysical RAM and swap usage, including cacheVirtual memory, page cache, swap (Part VIII)
df -hFree space per mounted file systemMounting, file systems (Part IX)
du -sh dirDisk usage of a directory treeFile allocation, directory trees (Part IX)
 
Reading `free` correctly$ free -h
              total    used    free   shared  buff/cache   available
Mem:           15Gi   4.2Gi   1.1Gi   210Mi       9.9Gi       10Gi
Swap:         2.0Gi      0B   2.0Gi
⚠Common Mistake
Panicking that "free" is low. Linux deliberately uses "spare" RAM as page cache (Part VIII) to speed up file access — that's the buff/cache column. It's instantly reclaimable, so the number that matters is available, not free. "Unused RAM is wasted RAM" is the kernel's philosophy.

System Activity: vmstat, iostat

CommandWhat it showsWatch for
vmstat 1Per-second processes, memory, swap, I/O, CPUsi/so (swap in/out) → thrashing (Part VIII); r (run queue length)
iostat -x 1Per-device I/O throughput and utilization%util near 100% → disk is the bottleneck
 
vmstat: watch swap columns to catch thrashing$ vmstat 1
 r  b   swpd   free  buff  cache   si   so    bi    bo   in   cs us sy id wa
 2  0      0  1.1G  120M  9.9G    0    0    12    30  400  900 15  4 80  1

The last line is a system in trouble: high si/so (swapping), high wa (CPU idle waiting on I/O), long run queue r. This is exactly the thrashing collapse from Part VIII, visible in real time.

Seeing the Kernel Boundary: strace, dmesg

CommandWhat it doesOS concept
straceTraces every system call a program makesThe user/kernel boundary made visible (Part I)
dmesgPrints the kernel's message ring buffer (boot, drivers, hardware, OOM)Boot process, drivers, kernel events (Parts I, X)
 
strace: literally watch a program cross into the kernel$ strace -f ./a.out
execve("./a.out", ...)          = 0
brk(NULL)                       = 0x55...        # heap setup (malloc, Part VII)
openat(AT_FDCWD, "data.txt", O_RDONLY) = 3       # open → fd 3 (Part IX)
read(3, "hello\n", 4096)        = 6              # the actual read syscall
write(1, "hello\n", 6)          = 6              # write to stdout
close(3)                        = 0
exit_group(0)                   = ?
⚑Interview Tip
strace is the single best learning and debugging tool for OS concepts. When someone asks "what system calls does X make?" you can show them. It's also how you debug mysterious failures — a program hanging in read(), or getting EACCES on a file, is obvious in the trace. Mentioning strace in an interview signals you actually work with systems, not just theory.

The Pseudo File Systems: /proc, /sys, /dev

Linux exposes kernel and hardware state as files you can read — the "everything is a file" philosophy taken to its logical end. No special API needed; just cat.

/proc
A virtual file system reflecting kernel and process state. It doesn't exist on disk — the kernel generates it on read. This is how ps, top, and free get their data.
/proc/[pid]
One directory per running process, named by PID — a live view of that process's PCB: /proc/1234/status (state, memory), /proc/1234/fd/ (its open file descriptors), /proc/1234/maps (its virtual memory layout, Part VII), cmdline, environ.
/sys
Exposes devices and kernel subsystems (the device model) — e.g. /sys/block/sda/queue/scheduler shows/sets the disk I/O scheduler (Part XII).
/dev
Holds device files: /dev/sda (a disk), /dev/null (the bit bucket), /dev/random, /dev/tty. Reading/writing these talks to drivers (Part X).
Reading kernel and process state as plain files$ cat /proc/cpuinfo                  # every CPU core and its features
$ cat /proc/meminfo                  # detailed memory stats (source of `free`)
$ cat /proc/self/maps                # THIS shell's virtual address space (Part VII)
$ cat /proc/1234/status              # process 1234's live PCB summary
$ ls /proc/1234/fd                   # its open file descriptors (Part IX)
$ echo hi > /dev/null                # discard output into the void
▣Key Concept
/proc and /sys are the kernel talking to you in file form. Every monitoring tool in this chapter is, underneath, just reading these virtual files and formatting them. Once you know that, you can get any system fact with cat — no special tooling required. This is the deepest expression of the UNIX "everything is a file" design.

⚑Practical Task
Run sleep 1000 &, note its PID, then explore: cat /proc/<pid>/status, ls -l /proc/<pid>/fd, cat /proc/<pid>/maps | head. Suspend and resume a foreground job with Ctrl-Z, bg, fg. Finally strace -c ls and read the syscall summary. You've now inspected a live process from the outside — exactly what top does.
