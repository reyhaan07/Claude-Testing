Part XVIWhat Happens When…

Every concept in this book was a puzzle piece. Here they assemble into complete pictures. Read each flow slowly and notice how many earlier parts it touches — that web of connections is mastery. These are also, almost verbatim, the "explain the whole path" questions asked in senior interviews.

…I turn on my computer?

  1. Power reaches the CPU, which begins executing firmware (UEFI/BIOS) baked into motherboard ROM.
  2. Firmware runs POST (power-on self-test), initializes hardware, and locates a boot device.
  3. It loads the bootloader (GRUB) from disk, which loads and decompresses the kernel into RAM.
  4. The kernel initializes memory management, the scheduler, and drivers, then mounts the root filesystem.
  5. It starts PID 1 (systemd), the first user process, which launches services, networking, and finally the login prompt.

Touches: firmware/boot (Part I), kernel init, filesystems (IX), init & PID 1 (II, XV).

…I open a program (double-click / type its name)?

  1. The shell/desktop calls fork() to create a child process (Part II).
  2. The child calls execve("/path/to/app"); the kernel replaces its image with the program.
  3. The kernel sets up a fresh virtual address space, memory-maps the executable and its shared libraries (demand-paged, not fully loaded — Part VIII).
  4. The dynamic linker resolves library symbols; the kernel sets the program counter to the entry point.
  5. The scheduler marks the process Ready; on dispatch it runs. Code and data page in as touched, via page faults.

…I execute a C program?

  1. fork+exec load the binary (flow 2). The kernel maps text (code), data, BSS, and sets up the stack with argc/argv/environment.
  2. The C runtime startup (_start → __libc_start_main) initializes the library, then calls your main().
  3. main runs, using the stack for locals and the heap for malloc, crossing into the kernel via system calls for any I/O.
  4. main returns a status; the runtime calls exit(), which flushes buffers and invokes the exit_group syscall; the kernel reclaims resources and leaves an exit status for the parent to wait() on.

…I call printf("hello")?

  1. printf is a library function: it formats the string ("%d" → digits) into a user-space buffer. No kernel involvement yet.
  2. The buffer is flushed to stdout when it fills, on a newline (if line-buffered to a terminal), or at exit. Flushing calls the write(1, ...) system call (Part I).
  3. The kernel copies the bytes to the terminal device (or file, if redirected) via its driver.

This is why buffering matters: a thousand printfs may cause far fewer write syscalls (Part I). If output is redirected to a file, it's fully buffered — you may see nothing until fflush or exit.

…I call malloc(size)?

  1. malloc is a library allocator, not a syscall. It first tries to satisfy the request from memory it already owns (its free list on the heap).
  2. If it needs more, it asks the kernel to grow the heap via brk/sbrk, or maps a fresh region with mmap (for large requests).
  3. The kernel extends the process's virtual address space but typically doesn't allocate physical RAM yet — pages are backed lazily on first access via page faults (flow 14), often via a shared zero page (copy-on-write).
  4. malloc returns a pointer into that space; the first write to each page triggers the actual physical allocation.
⚠Common Mistake
"malloc is a system call." It isn't — it's a user-space library routine that sometimes makes syscalls (brk/mmap) to get more heap. Most mallocs make no syscall at all, reusing already-mapped memory. That's why malloc is fast.

…I call fork()?

  1. The kernel allocates a new PCB (task_struct) and a new PID for the child.
  2. It copies the parent's context — open files, registers, and the address space logically, but via copy-on-write: parent and child share physical pages marked read-only (Part VIII).
  3. The child is placed on the ready queue. fork returns twice: child's PID to the parent, 0 to the child (Part II).
  4. The first time either process writes a shared page, the MMU faults and the kernel copies just that page — so the "copy" cost is paid lazily, only for modified pages.

…I call exec()?

  1. The kernel discards the current process's address space (text, data, heap, stack all gone) — but keeps the same PID and open file descriptors (unless marked close-on-exec).
  2. It memory-maps the new program's segments and its shared libraries (demand-paged).
  3. It resets the stack, sets registers, and points the program counter at the new program's entry.
  4. exec does not return on success — there's no old code to return to. Execution begins in the new program.

…I call read(fd, buf, n)?

  1. read traps into the kernel (Part I). The kernel uses fd to find the open-file entry (and its offset) and the inode (Part IX).
  2. If the requested blocks are in the page cache, data is copied to buf immediately.
  3. If not, the kernel issues a disk request, and the process blocks (state Waiting) while the disk works via DMA (Part X). The scheduler runs someone else.
  4. When the disk completes, it interrupts; the kernel copies the data into the cache and buf, marks the process Ready, and read returns the byte count, advancing the offset.

…I write to a file?

  1. write traps into the kernel, which locates the file via fd → inode.
  2. The data is copied into the page cache and the page marked dirty. write usually returns immediately — before the data is on disk.
  3. The kernel flushes dirty pages to disk later (background writeback), or on fsync, via the driver and DMA.
  4. Metadata changes (size, timestamps) are recorded; on a journaling FS they go through the journal first for crash safety (Part IX).

This "write returns before it hits disk" is why fsync exists and why a sudden power loss can lose recent writes still sitting in the cache.

…I press a keyboard key?

  1. The keyboard controller detects the keypress and raises a hardware interrupt (Part I/X).
  2. The CPU stops, switches to kernel mode, and runs the keyboard interrupt handler in the driver.
  3. The driver reads the scancode from the controller, translates it, and places the character in a buffer for the terminal/input subsystem.
  4. The kernel wakes any process blocked on input for that terminal (e.g. your shell in read); it becomes Ready and, when scheduled, receives the character.

…I move the mouse?

  1. The mouse sends movement deltas; the controller raises an interrupt for each batch.
  2. The driver's handler reads the deltas and posts input events to the kernel's input layer.
  3. The windowing system (a user-space process) reads those events, updates the cursor position, and determines which window is under the pointer.
  4. It delivers the event to the relevant application, which may redraw — the same interrupt-driven I/O pattern as the keyboard, just higher-frequency.

…a network packet arrives?

  1. The NIC receives the frame and DMAs it straight into a kernel receive buffer (Part XIII).
  2. The NIC raises an interrupt; the driver's handler does minimal work and schedules deferred processing (softirq/NAPI).
  3. The kernel network stack processes the packet up through IP and TCP (checksums, ordering, reassembly) and puts the payload in the destination socket's receive buffer.
  4. Any process blocked in recv()/epoll on that socket is marked Ready and gets the data when scheduled.

…RAM is full?

  1. On the next allocation/page fault needing a frame, the kernel finds no free frame.
  2. It reclaims memory: drop clean page-cache pages (cheap), and page out (swap) chosen pages to disk using a replacement policy (Part VIII).
  3. If reclaim keeps up, execution continues (slower). If working sets exceed RAM, the system thrashes — constant paging, collapsing throughput (Part VIII).
  4. If memory truly runs out (swap full too), the kernel invokes the OOM killer, which terminates a chosen memory-hungry process to survive.

…a page fault occurs?

  1. The CPU references a page whose page-table entry is marked not-present; the MMU raises a page fault exception (Part I).
  2. The kernel's handler checks the address is legal (else SIGSEGV), then finds a free frame (evicting one if needed, flow 13).
  3. It reads the page from disk (or zero-fills a new page), updates the page table (frame + present bit) and TLB.
  4. It restarts the faulting instruction, which now succeeds. (A minor fault needs no disk I/O; a major fault does — Part VIII.)

…a context switch happens?

  1. A trigger fires: timer interrupt (time slice up), a blocking syscall, or a higher-priority wakeup.
  2. The kernel saves the running process's registers and PC into its PCB and updates its state (Running → Ready/Waiting).
  3. The scheduler picks the next process; the kernel restores its registers/PC and switches the address space (loads its page-table base) — which may flush the TLB (Part II/VII).
  4. Execution resumes in the new process. The save/restore + cold caches are pure overhead.

…a process terminates?

  1. The process calls exit(status) (or receives a fatal signal). The kernel runs it in kernel mode.
  2. The kernel closes its file descriptors, frees its memory (address space, page tables), and releases other resources.
  3. It keeps a small zombie record (PID + exit status) until the parent wait()s (Part II). Any children are reparented to PID 1.
  4. When the parent reaps it, the PCB is freed and the PID becomes reusable.

…a thread blocks?

  1. The thread performs a blocking operation (I/O, lock acquisition, wait on a condition).
  2. The kernel changes that thread's state to Waiting and puts it on the relevant wait queue.
  3. The scheduler picks another runnable thread — possibly another thread of the same process (a cheaper switch, no address-space change) or a different process.
  4. When the awaited event occurs, the thread is moved to Ready; it runs again when scheduled. Note: only that thread blocks — with kernel threads, the process's other threads keep running.

…two threads modify the same variable?

  1. Each thread reads the variable into a register, modifies it, and writes it back — three non-atomic steps (Part III).
  2. If their steps interleave, one thread's read can predate the other's write, so one update is computed from a stale value and overwrites the other — a lost update (a race condition).
  3. The result depends on timing and is nondeterministic — correct on most runs, wrong occasionally.
  4. The fix: make the update atomic or wrap it in a critical section guarded by a mutex/atomic (Part V), so only one thread modifies it at a time.
⚑Interview Tip
These flows are the highest-value interview preparation in the book. "Walk me through what happens when you run a program / call malloc / a page faults" tests whether you truly connect the layers. Practice narrating three or four of these out loud until the cross-references (syscall → kernel → MMU → disk → scheduler) flow naturally. That fluency is exactly what "senior" sounds like.
