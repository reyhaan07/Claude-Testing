Part XI/O Systems

Computers are only useful because they talk to the outside world — disks, keyboards, screens, networks. But those devices are glacially slow next to the CPU. This part is about the three techniques the OS uses to move data to and from devices without letting the CPU sit idle waiting.

Devices, Controllers, and Drivers

Three layers separate your program from the physical hardware:

Device
The physical hardware — disk, NIC, keyboard.
Device controller
The electronics that operate the device, exposing a set of registers (data, status, command) the CPU reads/writes to control it.
Device driver
Kernel software that knows a specific controller's registers and presents a uniform interface (read/write/ioctl) to the rest of the OS. The driver is how the OS stays device-independent: swap the disk, swap the driver, everything above is unchanged.

Talking to controller registers happens two ways: port-mapped I/O (special in/out instructions and a separate I/O address space) or, more common today, memory-mapped I/O (device registers appear as ordinary memory addresses, so normal loads/stores control the device).

Three Ways to Do I/O

The central question: when a program requests slow I/O, what does the CPU do while the device works? The three answers are a progression from wasteful to efficient.

1. Polling (Programmed I/O) — Busy Waiting

The CPU repeatedly reads the controller's status register in a loop ("Are you done yet? Are you done yet?") until the device is ready, then transfers a word, and repeats. Simple, but the CPU burns 100% of its time spinning and transferring every byte itself. Fine only for very fast devices or the simplest systems.

2. Interrupt-Driven I/O

The CPU issues the I/O request and then goes off to do other work. When the device finishes, its controller raises an interrupt (Part I); the CPU stops, runs the driver's interrupt handler to transfer the data, then resumes what it was doing. The CPU no longer waits — it's interrupted only when there's actually something to do.

The remaining cost: one interrupt per data unit. For a disk block of thousands of bytes transferred a word at a time, that's still a lot of CPU involvement.

3. Direct Memory Access (DMA)

A dedicated DMA controller transfers a whole block directly between the device and RAM, without the CPU moving each byte. The CPU sets up the transfer (source, destination, count) and then is completely free; the DMA controller does the bulk move and raises a single interrupt when the entire block is done.

▣Key Concept — how interrupts and DMA improve performance
Interrupts free the CPU from waiting (no busy-poll) — it does useful work and is notified only when the device is ready. DMA additionally frees the CPU from doing the transfer — hardware moves the bulk data straight to RAM, and the CPU handles just one interrupt per block instead of one per word. Together they turn slow I/O from a CPU-monopolizing chore into a background activity. This is why your machine stays responsive while copying a large file.
⚠Common Mistake
Thinking DMA eliminates interrupts. It doesn't — it eliminates the CPU copying bytes and reduces interrupts to roughly one per block (the "transfer complete" signal), instead of one per word. The CPU still gets that final interrupt to know the data has arrived.

Buffering, Caching, and Spooling

Three techniques the kernel's I/O subsystem uses to smooth the speed mismatch and improve throughput. Don't confuse them:

TechniqueWhat it doesWhy
BufferingTemporarily holds data in memory between producer and consumer (device and app)Handles speed mismatch, allows different transfer sizes, and lets I/O and computation overlap
CachingKeeps copies of recently/frequently used data in fast memoryAvoids re-reading from slow storage (e.g. the page/buffer cache serves repeated file reads from RAM)
SpoolingQueues whole jobs to a buffer (usually disk) for a device that can't interleave requestsSerializes access to a device like a printer; lets many jobs be submitted and printed in turn
⚑Interview Tip
"Buffering vs caching?" A buffer holds data in transit (the only copy, moving from A to B); a cache holds a duplicate of data that lives elsewhere, to serve future requests faster. A buffer smooths a transfer; a cache avoids a repeat. Linux's page cache is a cache; the staging area a driver uses to assemble a disk block is a buffer.

Blocking, Non-Blocking, Synchronous, Asynchronous

These describe how an I/O call behaves from the program's point of view — endlessly muddled, so here they are precisely.

Blocking I/O
The call doesn't return until the I/O completes; the calling thread sleeps meanwhile. Simple to reason about; the default. (read() that waits for data.)
Non-blocking I/O
The call returns immediately — either with whatever data is ready now, or with "nothing available yet" (EAGAIN). The program must poll or retry. Useful for handling many connections in one thread.
Synchronous I/O
The program waits for the operation to finish (conceptually) before moving on — result is available when the call/notification completes.
Asynchronous I/O
The program issues the request and continues immediately; the OS performs the I/O in the background and notifies the program later (callback, signal, completion event). True "fire and forget, tell me when done."
▣Key Concept
Blocking vs non-blocking is about whether the call returns immediately. Sync vs async is about whether the work is done before you proceed. High-performance servers use non-blocking + event notification (epoll, kqueue) or full async (io_uring) to juggle thousands of connections with a handful of threads, instead of one blocked thread per connection (Part XIII).
