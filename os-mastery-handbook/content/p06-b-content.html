Part VIDeadlocks

A deadlock is a standstill: a set of processes each holding a resource the next one needs, in a circle, so none can ever proceed. Understanding the exact conditions that make it possible tells you precisely how to prevent it — and the Banker's Algorithm shows how to sidestep it entirely.

What Is a Deadlock?

What is it? A deadlock is a situation where a set of processes are each blocked, waiting for a resource that another process in the set is holding, so that none of them can ever make progress. The system is stuck — permanently, without intervention.

Simple intuition. A narrow bridge with one lane. Two cars enter from opposite ends and meet in the middle. Neither can pass, and neither will back up. Both wait forever. Each car holds "its half of the bridge" and needs "the other half" — held by the other car.

The Four Coffman Conditions

Deadlock is possible only if all four of these hold simultaneously. This is the single most important fact in the topic: break any one and deadlock cannot occur.

ConditionMeaningBridge analogy
1. Mutual ExclusionAt least one resource is non-shareable — only one process can hold it at a time.The lane fits one car.
2. Hold and WaitA process holds at least one resource while waiting to acquire others.A car sits on its half while waiting for the other half.
3. No PreemptionResources cannot be forcibly taken; they're released only voluntarily.No one can make a car reverse.
4. Circular WaitA closed chain of processes exists, each waiting for a resource held by the next.Car A waits on B, B waits on A.
▣Key Concept
All four Coffman conditions are necessary; together they are sufficient (given a single instance of each resource). Every deadlock prevention strategy works by making one of the four impossible. Circular wait is usually the easiest to attack (via resource ordering), which is why "lock ordering" is the number-one practical deadlock defense.

Resource Allocation Graph (RAG)

A resource-allocation graph pictures who holds and who wants what. Processes are circles, resources are squares. An edge R → P (assignment) means the resource is allocated to the process; an edge P → R (request) means the process is waiting for it.

⚠Common Mistake
"A cycle in the resource-allocation graph always means deadlock." Only if every resource type has a single instance. With multiple instances of a resource, a cycle is necessary but not sufficient — another process outside the cycle might release an instance and break it.

Four Ways to Handle Deadlock

  1. Prevention — structurally ensure one Coffman condition can never hold. (Conservative.)
  2. Avoidance — allow the conditions but never enter a state that could lead to deadlock; the OS checks each request (Banker's Algorithm). (Needs future knowledge.)
  3. Detection & Recovery — allow deadlocks, detect them with an algorithm, then recover (kill/rollback). (Reactive.)
  4. Ignore it — the "ostrich algorithm": pretend deadlocks never happen. Used by most general-purpose OSes (Linux, Windows) because deadlocks are rare and prevention is costly; reboot if one occurs.

⚑Interview Tip
"How do you prevent deadlock in real code?" Answer: lock ordering — establish a fixed global order for acquiring locks and always take them in that order. This breaks circular wait and is what real codebases actually do. The two-lock example deadlocks precisely because A and B take mutex1/mutex2 in opposite orders; force both to take mutex1 first and it's impossible.

Deadlock Avoidance and Safe States

Avoidance is less restrictive than prevention: it permits the four conditions but, before granting any resource request, checks whether doing so keeps the system in a safe state.

Safe state
There exists at least one ordering of all processes (a safe sequence) in which each can obtain its maximum needed resources, run, and finish — even if every process demands its maximum. A safe state guarantees no deadlock.
Unsafe state
No such sequence is guaranteed to exist. Unsafe does not mean deadlock — it means deadlock is possible. Avoidance simply refuses to ever step into unsafe territory.

Banker's Algorithm (Worked Numerical)

The classic avoidance algorithm (Dijkstra). Like a banker who never lends so much that they can't satisfy every client's credit line, the OS grants a request only if the resulting state is safe.

Data structures (for n processes, m resource types): Available[m] (free units), Max[n][m] (each process's maximum claim), Allocation[n][m] (currently held), and Need[n][m] = Max − Allocation.

A resource request. Suppose P1 now requests (1, 0, 2). Banker's checks: (i) Request ≤ Need P1 (1,2,2)? ✓  (ii) Request ≤ Available (3,3,2)? ✓. Tentatively grant: Available → (2,3,0), Alloc(P1) → (3,0,2), Need(P1) → (0,2,0). Re-run the safety check — it still finds the sequence ⟨ P1, P3, P0, P2, P4 ⟩, so the state is safe and the request is granted. (Had it been unsafe, the request would be denied and P1 made to wait.)

⚑Interview Tip
The mechanical recipe: (1) compute Need = Max − Allocation; (2) Available = Total − sum of Allocation; (3) run the safety loop with Work and Finish[]. If you can find any order that finishes everyone, it's safe. For a request, check Request ≤ Need and Request ≤ Available, pretend-allocate, then re-run safety. Practice this until it's automatic — it's a guaranteed exam question (see Part XIX for more).

Deadlock Detection and Recovery

If you neither prevent nor avoid, you must detect. For single-instance resources, detection = finding a cycle in the (wait-for) graph. For multiple instances, an algorithm similar to the Banker's safety check runs periodically: if some processes can never finish, they're deadlocked.

Recovery options once a deadlock is found:

  • Process termination — kill all deadlocked processes, or kill them one at a time (least-cost first) until the cycle breaks.
  • Resource preemption — forcibly take a resource from one process and give it to another, rolling back the victim to a safe checkpoint. Must avoid starving the same victim repeatedly.

Deadlock vs Starvation vs Livelock

 DeadlockStarvationLivelock
What happensProcesses blocked forever in a circular waitA process waits indefinitely while others proceedProcesses actively change state but make no progress
Are they running?No — all blockedOthers run; the victim doesn'tYes — busy, but uselessly
CauseAll four Coffman conditionsUnfair scheduling / resource policyOverly polite retry logic (both keep yielding)
AnalogyGridlocked intersectionAlways skipped in lineTwo people stepping aside in a hallway, repeatedly
FixBreak a Coffman conditionAging / fair schedulingAdd randomness / backoff
▣Key Concept
Deadlock: everyone stuck, no one moving. Livelock: everyone moving, no one progressing (they keep reacting to each other). Starvation: the system progresses, but one unlucky process never gets its turn. All three are "no progress" failures, but the mechanism differs — and so does the fix.
